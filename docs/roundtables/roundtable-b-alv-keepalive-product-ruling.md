## 基线判断原则

1. **"409h 无故障"是信号，但不是免死金牌。** 它证明当前系统在已知负载模式下的可靠性，但不能证明所有边界条件都已覆盖。罕见竞态和锁残留属于"压不死但能炸"型风险——需要对 blast radius 做独立判断。
2. **HCD 替代是真实的，但要区分替代关系。** HCD 替代的是"监控信号"，不是"修复动作"。某个 ALV 如果做的是修复，不能被 HCD 的监控替代；如果做的是监控，可以。
3. **产品视角 = 问两个问题**：(a) 这个改动修复的是什么用户痛苦？(b) 这个痛苦实际发生过吗 / 可能发生吗？

### ALV-002 (P2-02): rotate_log 竞态修复

| 维度 | 评估 |
|------|------|
| **风险本质** | 真实的并发 bug——两个进程同时 rotate 可能损坏或丢失日志 |
| **用户痛苦** | 如果触发：日志丢失 → 排查能力缺口 → 问题持续期间 Frank 无法回溯 |
| **409h 证据** | 0 次触发。竞态窗口极窄，触发概率低 |
| **HCD 能替代吗** | 否。HCD 监控的是进程存活，不是日志完整性。日志丢了 HCD 不会知道 |
| **致命性** | 低。最坏情况：该轮日志丢失，不影响服务运行，仅影响事后排查 |

> 这是"真实但罕见"的标准案例。不修也可以——409h 的统计证据是硬的。但要诚实地说：这是一个已知的、未修复的、但极低概率的 bug。

**裁决：降级 P2→P3。** 真实 bug，但 409h 零触发证明触发概率可忽略。不值得占用 P2 窗口，转入 P3"有空时"。

---

### ALV-003 (P2-03): restart lock rm -f 清理

| 维度 | 评估 |
|------|------|
| **风险本质** | supervisor 重启 keepalive → 发现残留 lock 文件 → 启动失败 → 服务完全离线 |
| **用户痛苦** | 服务不可用，直到人工介入删除 lock 文件 |
| **409h 证据** | 0 次触发——但这不代表安全。lock 残留的前提条件（异常 crash + 不干净退出）概率低但后果严重 |
| **HCD 能替代吗** | HCD 会**检测到** PID 消失并告警，但 HCD 不能**修复**这个状态——它不会删 lock 文件让服务重新启动 |
| **致命性** | 高。一旦触发 = 自动恢复链断裂。supervisor 的 auto-restart 被 lock 文件噎住 |

> 这是 5 项中唯一一个"低概率 × 高 blast radius"组合。和 ALV-002 不同：rotate_log 竞态只丢日志（不影响服务），restart lock 残留让服务直接无法启动。0.2h 工时投入一个 `rm -f` 防止全链路恢复卡死——ROI 极高。

**裁决：保留 P2。** 真实稳定性风险，工时极低，blast radius 高。修了可以永久消除一个人工介入场景。

### ALV-004 (P2-04): 端口配置化

| 维度 | 评估 |
|------|------|
| **当前状态** | Dashboard=9119, KeepAwake=8001，硬编码 |
| **用户痛苦** | 无。端口从未冲突，也不需要更换 |
| **触发场景** | 极特殊情况：换端口装第二个实例 / 端口被占用 / 产品策略要求改默认端口 |
| **改配置化的真实收益** | 可以把数字从脚本里移到配置文件里——仅此而已 |
| **不改的代价** | 真需要改端口时，改一行代码（grep + sed）比引入一个配置系统更快 |

> 端口配置化解决的是"未来某天可能想改端口"的假设性需求。目前的端口选择合理、无冲突、409h 无问题。没有用户因为端口硬编码而痛苦。这是教科书级的过度工程。

**裁决：归档。** 纯代码洁癖。端口不需要改，改了也不会更稳定。从 P2 移除，不转入任何优先级。

### ALV-005 (P2-05): cron 监控 log 写入时间

| 维度 | 评估 |
|------|------|
| **做什么** | cron 定时检查 keepalive 日志文件的 mtime，判断是否还在写入 |
| **监控什么** | "keepalive 是否还在活跃写日志" → 代理信号 → "keepalive 是否还活着" |
| **HCD 已经监控** | L0/L1: keepalive PID 存活检测（60s 周期，2 次连续失败 → 告警） |
| **哪个信号更好** | PID 存活 >> log 写入时间。PID 是直接信号，log mtime 是间接代理——keepalive 可能活着但不写日志（错误模式），也可能写了日志但已经死了（log flush latency） |
| **替代判断** | 是。HCD 的 PID 监控是更直接的"是否活着"信号，并且有外部 watchdog（每 5min 检查 HCD 心跳）做双重保险 |

> HCD 已经监控了你打算监控的东西，而且监控机制更好。再叠一层 cron check log mtime 是冗余监控——增加告警疲劳，降低信噪比。

**裁决：归档。** 被 HCD 的 L0/L1 PID 存活检测完全替代，且 HCD 信号更直接、更可靠。不重复造轮子。

## 补充说明

**如果有一天 keepalive 真的 crash 了而 lock 文件没清：** HCD 会告警，Frank 会收到飞书通知，人工上去 `rm -f` 然后 supervisor 自动拉起。恢复窗口：告警延迟 (60s) + 人工响应 (若干分钟)。修了 ALV-003 后恢复窗口：自动恢复 (<10s)。这就是 0.2h 投资的价值。

**关于 ALV-002（rotate_log 竞态）：** 如果未来真的触发了——日志丢失，Frank 排查困难——届时把这个 bug 从 P3 拉回来修。在有实际触发数据之前，409h 的证据足够强。
