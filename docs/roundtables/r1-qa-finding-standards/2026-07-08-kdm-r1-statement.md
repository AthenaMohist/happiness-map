# R1 发言：寇豆码（研发工程师）— QA 发现分级标准与处理流程

> 发言时间：2026-07-08
> 发言轮次：R1（第三轮，回应许清楚 & 高见远）
> 议题类型：A（Yes/No 决策 — 标准制定）

---

## stance

**基本认可高见远的架构修正方向，其修正版判定公式在工程上可执行，但有前提条件。** 「有成本申诉」优于「不可申诉 + 重新提交」——后者在工程实践中反而增加研发的上下文管理负担。8h 根因定位不现实，应改为「初步判定 + 进度同步」。补充 5 个产品/架构均未覆盖的工程落地维度。

整体姿态：**落地导向。标准写得好不如跑得通。** 我的发言不讨论要不要、应不应该——只讨论能不能在代码和工具链层面执行到位。

---

## concern_level: HIGH

理由：两份发言在逻辑层面都很完整，但都假设了一个理想工程环境——APM 已就绪、环境可随意调试、跨团队协作无摩擦、issue 系统有自动统计分析能力。这些假设在生产实践中不成立时，标准会从「指导」变成「负担」：

1. **判定公式的量化条件需要配套数据基础设施，否则只能用经验代替公式**——3x/10x 性能阈值在当前工程条件下如果没有 APM baselining，是不可执行的。
2. **「驳回不可申诉 + 重新提交」在工程上引起更多摩擦**——拆 context、污染质量数据、增加 issue 管理成本。
3. **SLA 的三档拆法方向对，但缺乏对不可控因素的 escape hatch**——跨系统 bug、非确定性 bug、第三方依赖阻塞，这些场景下 SLA 需要降级机制而非硬扛。

## specific_opinions

### 1. 评审高见远修正版判定公式的工程可操作性

高见远的修正公式（安全前置 + 性能量化 + 数据敏感度加权）框架上没有问题——研发可以直接对号入座执行。但这三个量化条件在工程上各有一套「落不了地」的场景：

#### 1.1 性能退化阈值：3x / 10x 基准值

**工程判断**：「P95 响应时间恶化 ≥ 3x 基准值」是可操作的条件——前提是 **per-endpoint 的历史 P95 baselining 已经跑起来了**。如果当前项目还没有 APM（Application Performance Monitoring）或等价的 metrics 采集，这就是空转。

**建议**：要么在标准中注明「性能退化判定依赖 APM baselining 已就绪。未就绪期间由研发基于经验判断，依据如下 fallback 表」，要么给一个不依赖工具的退化阶段 fallback：

| 响应时间 | 对应级别 | 说明 |
|----------|:---:|------|
| < 1s | MINOR | 用户可能注意到 |
| 1s – 5s | MAJOR | 体验严重退化 |
| > 5s 或 OOM/崩溃 | BLOCKER | 功能实质上不可用 |

研发角度：简单粗暴但立即可执行。工具链补齐后再切换为精确的 3x/10x 公式。

#### 1.2 数据敏感度加权：「涉及资金/关键业务数据」

**工程判断**：可以执行，但「关键业务数据」需要有白名单，否则变成研发和产品之间的第二轮争议。

**建议**：在标准附录中维护一个数据敏感度分类表：

| 敏感度 | 包含数据 | 遇到一致性 bug 时 |
|--------|---------|:---:|
| S 级 | 资金流水、用户资产、订单金额 | 自动 +1 级 → 最低 MAJOR |
| A 级 | 用户基础信息（手机/邮箱/实名）、权限 | 自动 +1 级 |
| B 级 | 用户行为日志、统计指标 | 不加权 |
| C 级 | 内部配置、管理后台数据 | 按正常公式 |

工程实现就是给 issue 系统加一个 `data_sensitivity` 字段，关联到这个分类表。QA 提交时选分类，系统自动计算加权。人工判断容易出错且难追溯。

#### 1.3 安全漏洞前置判定

**工程判断**：方向完全正确。但「是否为安全漏洞」这个判定本身对 QA 有技能要求。如果 QA 团队没有安全背景，这条规则会空转。

**建议**：配套一个 minimal viable 的安全漏洞 checklist，至少覆盖 OWASP Top 10 大类（SQL 注入、XSS、认证绕过、敏感信息泄露、CSRF、SSRF 等）。QA 不需要做渗透测试，只需要能识别「这个 issue 看起来像是 A3: Injection → 标记安全相关」。

### 2. 评审驳回机制：不可申诉 vs 有成本申诉

**直接亮观点：高见远的「有成本申诉」（reopen + 新证据 + 产品直接裁定）优于许清楚的「驳回不可申诉 + 重新提交为新 issue」。**

这不是产品/架构层面的理由，是工程师直接面对的操作现实：

#### 2.1 「驳回不可申诉 + 重新提交」在工程上的问题

- **context 被分裂**：issue #42 被驳回关闭，QA 新建 #67（内容几乎一样）。我看 #67 会说「这不就是 #42 吗」。争论并不会消失——只是从 1 个 issue 的评论区转移到了 2 个 issue 之间。
- **质量数据被污染**：一个真实 bug 被关闭为 `wont fix` + 另一个 open issue 跟踪同一个问题。统计 MAJOR+ 密度时数据不准。
- **接手的人没有完整 context**：后来接手这个模块的人看到 #42 closed，可能根本不知道 #67 是同一个问题的延续。

#### 2.2 「有成本申诉」对研发来说反而负担更小

高见远的方案：
- QA reopen，带新证据，同一个 issue
- 跳过二轮研发评估，产品（许清楚）直接裁定
- 申诉的门槛是「新证据」——不能空手争论

**研发视角我支持这个**：一条 issue、完整链路、产品裁定后我照办。我不需要在两个 issue 号之间做 mental mapping，不需要猜「这个是不是上次那个」。

#### 2.3 研发希望多大的裁量权？

**说清楚我（研发）想要什么、不想要什么：**

| 权力 | 要/不要 | 理由 |
|------|:---:|------|
| 「by design」判定权 | ✅ 要 | 这是研发专业判断的核心。产品不应 override「这功能就是这么设计的」|
| 「cost > benefit」关闭权（仅 SUGGESTION/MINOR） | ✅ 要 | 只有写代码的人才知道改一个"看起来简单"的东西要牵动多少模块 |
| 级别修正权（降级） | ✅ 要 | 但有条件：降 BLOCKER→MAJOR 时必须写理由，自动通知产品。敢降就敢解释 |
| 最终裁决「这个 bug 到底重不重要」 | ❌ 不要 | 那是产品的事 |

高见远提出的「研发降级时自动通知产品」机制我完全支持。信息对称就够了——不需要审批，不需要阻塞，但需要可见。

### 3. 评审 SLA：8h 定位不现实

高见远将 BLOCKER SLA 拆为「4h 响应 + 8h 根因定位 + 24h 方案」，方向对，但 **8h 根因定位作为 hard SLA 是 unrealistic 的**。

#### 3.1 根因分析超过 8h 的典型场景（研发每天都在经历）

| 场景 | 为何超过 8h | 频率 |
|------|------------|:---:|
| **跨系统联级故障** | Bug 表现在前端白屏，根因在微服务 C 的缓存层 → 服务 D 的数据管道 → DB 的慢查询。跨 4 层追溯，每层都要抓日志、在对应环境复现、排除假设 | 最常见 |
| **非确定性/竞态 bug（Heisenbug）** | 复现率 1/100，改日志级别可能改变时序导致不再复现。复现本身就可能耗半天 | 常见 |
| **数据依赖型 bug** | 只有特定用户在生产环境的数据形态才触发。安全地拿到那份数据（脱敏、导出）就需要运维配合 | 常见 |
| **第三方依赖排查** | SDK 升级引入的 bug，需要读第三方源码或等厂商回复 | 偶发但耗时 |
| **基础设施层问题** | 网络/DNS/负载均衡配置变更。研发可能没有直接的基础设施访问权限，需要 SRE/运维介入 | 偶发但关键 |

#### 3.2 替代方案：「初步判定 + 进度同步」

将「8h 根因定位」改为「8h 初步判定（Initial Diagnosis）」：

- **8h 内必须产出**：
  - 问题涉及哪些系统/模块？
  - 已排除哪些假设？
  - 当前排查方向是什么？
  - 是否需要跨团队协调？需要找谁？
  - 预计还需要多少时间完成根因定位？

- **如果 8h 仍无法定位根因**：
  - 研发主动升 flag
  - 产品做 stakeholder 沟通
  - Frank 决策：等定位结果还是暂缓发版

**这不是降低标准，是对复杂 bug 非线性的诚实。** 你查到第 6 小时以为自己找到了，结果发现是更深层的东西——这种情况在有多个依赖链的系统中极其常见。

#### 3.3 关于修复时限 vs 方案时限

高见远把「修复时限」改为「方案时限」——完全正确。补充一个具体数字：**一个涉及跨 2+ 模块的 BLOCKER，从定位到修复到回归，正常节奏是 2-3 个工作日。** 24h 只能覆盖根因简单 + 改一行代码 + 回归无影响的那种 BLOCKER。把标准设成 24h 硬指标，要么研发 rush 出质量差的 hotfix（然后修好一个 BLOCKER 引入两个新 BLOCKER），要么标准名存实亡。

### 4. 补充：产品/架构遗漏的工程落地维度

以下 5 个维度既不在许清楚的发言中、也不在高见远的发言中，但研发认为必须在分级标准中体现——否则标准落不了地：

#### 4.1 可复现性 —— 整个 SLA 链条的前提

许清楚和高见远都在谈「QA 发现 → 研发评估 → SLA 计时」，但都没提一个前提：**如果 QA 提的 issue 不可复现，SLA 时钟应该暂停还是继续走？**

**研发视角**：我在一个无法复现的 bug 上花 4h「响应」然后说「无法复现」，这不是 SLA 达标——这是浪费。可复现性是整个链条的燃料，没有它，所有时限都没有意义。

**建议**：按级别定义最小复现要求：

| 级别 | 最小复现要求 | QA 补充时限 |
|------|-------------|:---:|
| BLOCKER | 明确的 step-by-step 复现步骤 | 2h 内补充（否则降级处理） |
| MAJOR | 复现步骤或充分的日志/截图/视频 | 1 工作日内 |
| MINOR | 描述性即可 | - |
| SUGGESTION | 不要求 | - |

规则：如果 QA 无法在规定时限内提供复现步骤，SLA 计时暂停，级别自动降一级。

#### 4.2 修复的发布门禁

标准里只说「修复」，没定义修复后怎么上线。对研发来说这是个真实问题：修好了一个 BLOCKER，能不能直接推到生产？

**建议**：按修复级别定义最小验证门禁：

| 级别 | 代码审查 | 测试门禁 | 发布策略 |
|------|:---:|------|------|
| BLOCKER | ✅ 必须第二人 review | staging smoke test | 灰度发布（如有能力）|
| MAJOR | ✅ 推荐 review | staging 回归测试 | 常规发布 |
| MINOR | 不强制 | 常规 CI | 常规发布 |
| SUGGESTION | 不强制 | 常规 CI | 常规发布 |

这不是给研发加负担——是防止「修了一个 BLOCKER，引入两个新 BLOCKER」的经典悲剧。BLOCKER 的修复必须经过第二双眼睛。

#### 4.3 环境差异 —— Bug 只在某个环境出现

QA 在 staging 发现 → 研发在 dev 无法复现 → 怎么办？这个场景极高频，标准需要给处理路径：

**建议**：
- 如果研发在 dev/local 无法复现，研发有权申请 staging 环境调试权限
- 如果 bug 涉及生产数据、需要脱敏后才能调试，SLA 计时应暂停等待数据准备
- 不应该在「无法复现但 QA 坚称存在」的场景下让研发背 SLA

#### 4.4 跨团队协调成本应计入 SLA 计量

高见远提到第三方依赖放宽到 48h，但即便所有系统都是内部自研的，跨团队 handoff 本身就有摩擦成本。

**典型场景**：BLOCKER 4h 响应 → 我判断是 DB 层问题 → 提给 DBA → DBA 有自己的队列和优先级 → 排查要排到第二天。我的 4h 响应准时了，但端到端的定位时间远超 8h——而且不是任何人的错。

**建议**：SLA 增加跨团队规则：
- 经研发判定需要跨团队（DBA/运维/SRE/其他微服务团队），handoff 确认时间计入响应时限
- 被调团队的响应时限独立起算——BLOCKER 级别的跨团队 handoff，被调方的响应时限也是 4h
- 如果被调团队无法按时响应，研发负责升 flag 通知产品协调

#### 4.5 技术债务追踪 —— 需要工具化

高见远的「同一模块连续 3 版本 ≥ 3 个 MAJOR+ → Architecture Review」逻辑对，但执行仰赖人工统计 → 大概率不会发生。

**建议**：这是工具链的事，不是靠文档能解决的：
- issue 系统的「所属模块」字段必须是 required field（不能 optional）
- 一个简单的 Dashboard 自动统计 per-module MAJOR+ 密度
- 超过阈值 → 自动通知架构师

研发可以负责实现这个追踪工具，但需要产品确认这是一个正式需求——不是「nice to have」。

## 总结

我对两份发言的评价：

- **许清楚的 4 级框架**：骨架正确，但「驳回不可申诉」需要在工程层面修——不是原则问题，是操作问题。
- **高见远的架构修正**：方向我全部支持。性能量化、安全前置、有成本申诉、方案时限——这些都是从工程可行性出发的正确修正。但量化条件需要配套落地工具，否则公式再好也是纸上画画。

**我发言的五句话版**：

1. 高见远的修正公式工程上可执行，但性能 3x/10x 需要 APM baselining + 数据敏感度需要白名单 checklist，否则执行靠感觉。
2. 「有成本申诉」比「不可申诉 + 重新提交」对研发负担更小——一条 issue、完整 context、产品裁定、我们照办。
3. 8h 不应该是「根因定位」而应该是「初步判定 + 进度同步」——复杂 bug 的根因不是线性的，8h 不可能预判所有情况。
4. BLOCKER 修复必须有代码 review + staging smoke test 门禁——这是研发自己要求的安全网。
5. 标准缺失了可复现性、环境差异、跨团队 handoff 三个工程关键路径，没有这些，SLA 在真实场景中反复被打破。

等待 QA 从执行视角补充，以及 Frank 在 R2 做平衡。
