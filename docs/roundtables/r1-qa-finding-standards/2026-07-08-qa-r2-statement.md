> 发言时间：2026-07-08

## stance

**许清楚在 3 个分歧点上让步，方向完全正确——QA 不做姿态，给实操落地的具体设计。**

R1 我提出「有成本申诉」替代「驳回不可申诉」——许清楚 R2 全面接受，寇豆码从研发视角确认「负担更小」，三方共识达成。这是本次 roundtable 对 QA 最重要的胜利。

但 R2 的 4 个待回应分歧点不因许清楚让步而消失——它们从「要不要」变成了「怎么做」。我的回答聚焦在 QA 每天的操作面上。

## concern_level: MEDIUM（此时 → LOW）

理由：R1 时的核心风险（QA 失语、SLA 空转、标准不可用）因许清楚让步得到结构性缓解。剩余风险是**执行层面的**——如果配套机制不到位（申诉模板、SLA 升级路径、bug report 标准化），共识框架仍然落不了地。但这不是「会不会出事」，而是「做完没做完」——所以是 MEDIUM。

### 分歧 1：驳回机制 — QA 的最低保障

> 对应问题：无论最终方案是什么（许清楚已让步为「有成本申诉」），QA 的最低保障是什么？

**① 立场：QA 的最低保障不是「申诉权」，是「信息不丢失」——并且申诉机制本身必须有防滥用设计。**

许清楚 R2 已全面让步，接受「有成本申诉」方案。**QA 感谢三方（许清楚/高见远/寇豆码）对 QA 职业尊严的尊重。** 但让步是决策层面的——QA 需要在执行层面明确 4 项最低保障，缺失任何一项，申诉权都会在实际操作中被架空：

| # | 保障项 | 具体要求 | 为什么是最低线 |
|---|--------|---------|--------------|
| 1 | **申诉模板**（QA 可填写的标准化表格） | 必须包含：申诉理由（从 4 类中选择：新复现证据 / 新影响面分析 / 新用户反馈 / 研发驳回理由与事实不符）、附带新证据的文件名/链接、期望裁定结果（恢复级别 / 重新评估） | 没有模板，申诉变成写作文——QA 花 30 分钟写申诉文案，最终不写的概率 >50% |
| 2 | **产品裁定时效** | BLOCKER 申诉 → 产品 1 工作日内裁定；MAJOR 申诉 → 产品 2 工作日内裁定；超过时效未裁定 → 自动按 QA 申诉请求处理（恢复至 QA 主张的级别） | 如果没有产品裁定时效，申诉进入黑洞——QA 2 周后还在等裁定，bug 已经发版了 |
| 3 | **申诉数据对 QA 反向透明** | QA 需要能看到自己被驳回 bug 的申诉率、申诉成功率、按模块/按研发分组的驳回模式 | 这是 QA 自我校准的工具——如果我对某个模块的 bug 申诉率 > 30% 但成功率 < 20%，说明我对那个模块的级别判断有问题，需要和研发对齐 |
| 4 | **「接受驳回」不是「承认错误」** | Issue 系统标注 `accepted_rejection` 时，不隐含任何「QA 判断错误」的语义——只是「QA 在获得研发信息后认同此 bug 不需要修复」 | 如果「接受驳回」被等同于「QA 提了无效 bug」，QA 会抗拒接受任何驳回——即使研发有充分理由。去掉道德标签，保留操作动作 |

**② 让步条件：如果产品裁定时效无法保证（许清楚本人不在或有更紧急事务），接受降级方案。**

降级方案：产品缺席时，BLOCKER 申诉由技术负责人（架构师高见远）裁定，MAJOR 申诉由研发负责人裁定。这不理想（产品裁定是从用户视角出发，技术负责人可能存在架构偏见），但比「申诉无人处理」好。条件：技术负责人裁定后，许清楚回归时需在 3 个工作日内 review 所有缺席期间的裁定——可以推翻，推翻后的重复工作由推翻方负责协调。

**③ 一句话理由：申诉权没有配套执行机制 = 给你一个没有钥匙的锁——理论上存在，实际上打不开。**

### 分歧 2：SLA 超时处理 — QA 的紧急升级路径

> 对应问题：如果 BLOCKER 4h 没人响应，QA 应该怎么做？定义 QA 的升级路径（谁→谁→谁）、每个升级阶梯的时间。

**① 立场：QA 的升级路径是双层设计——正常路径（依赖 SLA 计时器自动触发）和紧急路径（QA 手动升级）。双层缺一不可，因为工具会坏、人会忘。**

#### 第一层：系统自动升级（依赖工具化）

这是理想路径——不应该依赖 QA 手动盯着时钟：

```
BLOCKER 提交 → 系统自动计时
  ├── 2h 无研发 acknowledge → 系统自动 @研发 + @研发 team lead
  ├── 4h 无研发 acknowledge → 系统自动 @产品（许清楚）+ 标注 SLA:breach
  ├── 8h 无研发 acknowledge → 系统自动 @Frank + 标注 SLA:critical_breach
  └── 24h 无任何响应 → 自动进入 Frank 决策队列（是否暂缓发版）
```

MAJOR 路径（更宽松的阶梯）：

```
MAJOR 提交 → 系统自动计时
  ├── 1 工作日无研发 acknowledge → 系统自动 @研发 team lead
  ├── 2 工作日无响应 → 系统自动 @产品
  └── 3 工作日无响应 → 进入产品待办池（本周内必须处理）
```

**但这种自动升级依赖 issue 系统有 SLA tracking 能力。在这之前，QA 需要手动升级路径。**

#### 第二层：QA 手动升级路径（工具化前的现实）

这是 QA 的实操手册——每一个 QA 团队成员应该知道「如果 bug 没人看，我下一步干什么」：

```
BLOCKER 手动升级路径：

QA 提交后 4h，未收到研发 acknowledge
  → [阶梯 0，4h 时点] QA 在 issue 中追加评论：「@研发 4h 响应时限已到，请 acknowledge 并给出初步判定」
  
  → [阶梯 1，6h 时点，+2h 后] QA 直接 IM（企业微信/Slack/DingTalk）通知研发 + 抄送研发 team lead
      消息模板：「BLOCKER #XX（标题）已提交 6h 未响应。4h SLA 已超时。请确认是否看到此 issue。」
  
  → [阶梯 2，8h 时点，+2h 后] QA 通知产品（许清楚）：
      消息模板：「BLOCKER #XX 已提交 8h，研发未 acknowledge。标准 4h 响应时限已超时 4h。请产品介入协调。」
      QA 必须附带：issue 链接、bug 摘要（一句话）、首次提交时间、QA 尝试联系研发的时间点
  
  → [阶梯 3，12h 时点，+4h 后] QA 通知 Frank：
      消息模板：「BLOCKER #XX 已提交 12h，研发和产品均未给出明确处理方案。标准 4h 响应时限已超时 8h。请求 Frank 决策：等 or 暂缓发版 or 指定负责人。」
      此时 QA 不再追踪具体时钟——从这个点开始是项目管理问题，不是 QA SLA 问题。

MAJOR 手动升级路径（更宽松）：

QA 提交后 1 工作日，未收到研发 acknowledge
  → [阶梯 1] QA 在 issue 中追加评论提醒
  → [阶梯 2，2 工作日] QA IM 通知研发 + 抄送 team lead
  → [阶梯 3，3 工作日] QA 通知产品
  → [阶梯 4，5 工作日] 进入产品待办池，QA 不再追踪
```

#### 升级路径中的 QA 行为底线

| 规则 | 理由 |
|------|------|
| QA 每次升级必须附带 issue 链接 + 提交时间 + 已等待时长 | 避免「QA 自己没记清楚时间，过早升级」——数据说话 |
| QA 不在升级消息中讨论 bug 内容——只讨论响应状态 | 内容讨论留在 issue 评论里，升级消息保持短（3 行以内），否则研发/product owner 看完需要 5 分钟 → 不会看 |
| QA 不使用「紧急」「严重」「救命」等情绪化词汇 | 升级通道是冷静的流程触发器，不是情感呼救——如果 QA 喊狼来了 3 次，第 4 次没人听了 |
| 如果 BLOCKER 是非工作时间提交的——参照许清楚规则，计时从下个工作时段的第 1 小时开始 | 这已经协商一致，QA 尊重研发的正常作息 |

**② 让步条件：如果团队规模小（≤10 人，没有 team lead 层），升级路径允许简化。**

简化版：
- 4h → @研发（IM）+ @产品（IM 抄送）
- 8h → @Frank

无 team lead 层时，QA 不能假装有中间层——直接跳到有决策权的人。代价是噪声更多（产品/Frank 被 @ 的频率更高），但这比「QA 不知道找谁」好。

**③ 一句话理由：SLA 如果没有「超时了然后呢」，就是一个只能在 PPT 上好看的数字——QA 的升级路径是 SLA 的牙齿。**

### 分歧 3：「用户可见」判定 — QA 的实操化建议

> 对应问题：QA 的三维判定（用户可感知 + 数据完整性 + 系统健康度）如何与许清楚「用户可见第一刀」共存？判定顺序是什么？

**① 立场：三维判定是许清楚「用户可见」的补充安全网，不是替代。具体判定顺序如下——这是一个 QA 在提交 bug 时可以逐条走的 checklist：**

```
QA 提交 bug 时的判定顺序（按优先级排）：

Step 1: 安全漏洞？ ──→ 是 ──→ 最低 MAJOR（高见远修正）
  │                              ├── 认证绕过 / 数据泄露 / 可远程利用注入 → BLOCKER
  │                              └── 其他 OWASP Top 10 → MAJOR
  │
  └── 否 ↓

Step 2: 用户可感知？ ──→ 是 ──→ 进入许清楚原始公式
  │                              ├── 功能阻断 AND 无 workaround → BLOCKER
  │                              ├── 功能阻断 BUT 有 workaround → MAJOR
  │                              └── 不影响核心任务 → MINOR
  │
  └── 否 ↓

Step 3: 数据完整性受影响？
  │         ├── 涉及 S 级数据（资金/资产/订单）──→ BLOCKER
  │         ├── 涉及 A 级数据（用户基础信息/权限）──→ MAJOR
  │         └── 涉及 B/C 级数据 ──→ 按正常公式
  │
  └── 否 ↓

Step 4: 系统健康度退化？
  │         ├── OOM / 崩溃 / 错误率突增 5x+ ──→ BLOCKER
  │         ├── 内存泄漏（预计 48h 内 OOM）/ 错误率 2-5x ──→ MAJOR
  │         └── 轻微退化（错误率 < 2x，无用户影响）──→ 进入 Step 5
  │
  └── 否 ↓

Step 5: 纯主观偏好？
        ├── 代码风格 / 命名 / 结构优化 / 内部重构 ──→ SUGGESTION
        └── 不满足以上任何一条 ──→ 默认 MINOR + 标注 triage_needed
```

**关键设计解释：**

- **Step 1（安全漏洞）在最前面**——因为安全漏洞一旦被「用户不可见」过滤掉就回不来了。这是高见远的修正，许清楚 R2 已接受。QA 执行时不需要懂安全——对照寇豆码的 OWASP Top 10 checklist 判断即可。

- **Step 2（用户可感知）是许清楚的核心路径**——处理 80-90% 的正常 bug。如果用户能看到/感知到问题，直接走许清楚的公式。这条路径不需要 QA 纠结「数据完整性」「系统健康度」——走最简单的逻辑。

- **Step 3-4（数据完整性 + 系统健康度）是 QA 的「安全网」**——只有 Step 2 回答「否」时才进入。这两条捕获的是「用户还没感觉到但 QA 知道会出事的 bug」：数据已经写错了（用户可能 2 小时后才发现）、内存已经在泄漏（用户可能明天才遇到 OOM）。

- **Step 5 是终点**——如果前面 4 步都走完了仍然不匹配任何条件，那就是真正的 SUGGESTION（纯主观/代码层面）。

> **这个顺序的设计原则：「优先捕获不可逆的损害」，其次「用户可感知的损害」，最后才是「纯主观偏好」。安全漏洞不可逆（被利用了才可见），数据错误不可逆（数据写错了不会自己恢复），系统健康度退化不可逆（泄漏不会自己停）。用户可感知的问题——用户已经感受到了，修复窗口还在。**

**② 让步条件：如果许清楚坚持 Step 2 必须是唯一入口（不接受 Step 3-4 的独立路径），QA 接受一个降级方案。**

降级方案：Step 3（数据完整性）和 Step 4（系统健康度）不作为独立的判定路径，而是作为 Step 2 的「推断扩展」——即「数据完整性受影响」视为「用户将在数据被使用时感知到」，「系统健康度退化」视为「用户将在 OOM/崩溃时感知到」。效果上，Step 3-4 仍然将对应的 bug 推向 MAJOR/BLOCKER——只是措辞上仍框在「用户可见」的语义下。**QA 不争措辞，争结果。**

**③ 一句话理由：「用户可见」是第一刀——我完全同意；但有些伤是内出血——QA 知道在流血，用户要等倒下了才知道。**

### 分歧 4：QA Bug Report 模板标准化

> 对应问题：输出一个 QA Bug Report 的最小字段集（不超过 10 个必填字段）。每个字段标注「QA 填」还是「系统自动填」。

**① 立场：最少 10 个字段，按「QA 提交时需要填什么」排序——不是按重要性，是按填写顺序。**

| # | 字段名 | 填写者 | 字段类型 | 说明 |
|---|--------|:---:|------|------|
| 1 | **Bug ID** | 系统自动 | 自增/时间戳 | 不可编辑，不可重复 |
| 2 | **标题** | QA 填 | 单行文本（≤100 字） | 格式要求：「[模块] 条件 → 结果」或「[模块] 预期 vs 实际」。例如「[支付] 余额充足时点击支付按钮无响应」。不允许「it doesn't work」——标题必须让接手的人不点进 issue 就知道发生了什么 |
| 3 | **级别** | QA 填 | 下拉单选（BLOCKER / MAJOR / MINOR / SUGGESTION） | 系统根据 §分歧3 的判定顺序提供速查指引（侧边栏或 tooltip），但不自动判定 |
| 4 | **所属模块** | QA 填 | 下拉单选（从项目模块列表中选择） | Required。寇豆码要求的「技术债务追踪」前提——没有模块标注就无法出模块质量报告。下拉列表由技术负责人维护，QA 不维护 |
| 5 | **环境信息** | 系统自动（预填）+ QA 补充 | 多字段组合 | 系统自动采集：提交时间、当前 staging 版本号、QA 设备类型（从 user-agent 推断）。QA 补充：操作系统版本、浏览器版本、是否有特殊配置（如 VPN、特定账号角色）。BLOCKER/MAJOR 必须完整填写，MINOR 可简略，SUGGESTION 不要求 |
| 6 | **复现步骤** | QA 填 | 编号列表（最小 1 步） | 格式：Step 1 → Step 2 → Step 3。BLOCKER/MAJOR 必须精确到「点击哪个按钮」「输入什么数据」。研发应能照着步骤独立复现——如果不行，驳回理由不能是「cannot repro」，只能是「need more info」（需要 QA 补充后 SLA 时钟暂停） |
| 7 | **预期行为 vs 实际行为** | QA 填 | 两个文本框 | 左：「预期：点击支付按钮后弹出支付确认页」。右：「实际：点击后无响应，控制台报错 `Uncaught TypeError: Cannot read properties of null`」。BLOCKER/MAJOR/MINOR 必填，SUGGESTION 建议填 |
| 8 | **复现率** | QA 填 | 格式「N/M」+ 下拉选择 | 必须填：测试次数 M 和复现次数 N，如「3/10」。下拉选项：「每次必现 / 概率性复现（N/M）/ 偶发（< 10%）/ 仅复现 1 次」。BLOCKER/MAJOR 必填——没有复现率数据的 BLOCKER 不应被接受 |
| 9 | **附件** | QA 填 | 文件上传 / 粘贴链接 | 截图（标注关键区域）、录屏（≤30s GIF/MP4）、日志片段（不粘贴整个日志——只粘贴相关行并标注时间戳）、HAR 文件（如果是前端网络问题）。BLOCKER：录制是强建议（不是强制——有些场景无法录屏，如系统级崩溃）；MAJOR：截图强建议 |
| 10 | **数据敏感度** | QA 填 | 下拉单选（S / A / B / C / 不涉及） | 寇豆码的 S/A/B/C 分类。QA 初选，研发可修正。如果涉及 S 级（资金/资产），系统自动在标题旁加红色「💰」标记。如果不确定——选择「不确定」而不是 B/C——系统对「不确定」标记为 triage_needed，由研发评估时确认 |

#### 系统自动填充的隐藏字段（QA 不需要填，但系统在后台自动记录）

| 隐藏字段 | 来源 | 用途 |
|---------|------|------|
| 创建时间 | 系统时间戳 | SLA 计时起点 |
| 提交人（QA） | 系统身份 | 责任归属 + 申诉数据追踪（按 QA 分组的驳回率/申诉率） |
| Issue 状态 | 系统状态机 | NEW → OPEN → ...（QA R1 §4.1 的状态机） |
| 当前受理人（研发） | 系统自动分配或手动指定 | SLA 响应计时对象 |
| 关联 issue（重复/父级/子级） | QA 手动链接 | 重复 bug 去重、申诉时的原 issue 关联 |

#### 模板需要避开的坑

| 坑 | 表现 | 正确做法 |
|----|------|---------|
| 字段太多 | 15+ 必填 → QA 花 15 分钟填一个 SUGGESTION → QA 不提交 | 10 个字段是上限。MINOR/SUGGESTION 可简化部分字段（如复现步骤、复现率不强制） |
| 描述性字段变成散文 | 「预期行为」写 500 字 | 标题 ≤ 100 字，每个描述字段有隐藏字数上限（200 字），超出提示「请精简」 |
| 「级别」字段没有速查辅助 | QA 每次自己查文档判定 | 系统在级别下拉框旁边显示一个「？」按钮，点击弹出分歧 3 的判定顺序 checklist（5 步） |
| 复现步骤变成「登录 → 操作 → 报错了」 | 无法复现 | 模板中有 placeholder 示例：「Step 1: 打开 https://staging.example.com/payment → Step 2: 输入账号 test_user_01，密码 xxx → Step 3: 点击『立即支付』按钮 → Step 4: 观察到页面无响应，控制台输出错误（见附件截图）」 |

**② 让步条件：如果团队当前使用的 issue 系统（如 GitHub Issues / Jira / Linear / 飞书多维表格）不支持部分字段类型（如「嵌套字段」「自定义下拉」），QA 接受简化版。**

简化版（6 字段）：标题 + 级别 + 模块 + 复现步骤 + 预期 vs 实际 + 附件。剩余字段（环境信息、复现率、数据敏感度）改为建议填写，写入模板的「description」区域但不在 issue 列表视图中显式展示。**这不是放弃标准——是承认工具限制。要求是：工具升级后回填这些字段。**

**③ 一句话理由：模板的价值不是让 QA 多填东西——是让研发少问东西（每个 QA 没填的字段 = 研发要花 15 分钟追问 = SLA 计时在等 QA 回复中消耗）。**

## 总结

### 四个分歧点，QA 的回应一句话版

| 分歧 | QA 一句话回应 |
|------|-------------|
| 1. 驳回机制底线 | 申诉权需要模板、产品裁定时效、QA 数据透明、「接受驳回不含道德判断」——四者缺一，申诉权空转。 |
| 2. SLA 升级路径 | 系统自动升级（理想）+ QA 手动升级（现实）——双层路径：4h→研发 + 6h→team lead + 8h→产品 + 12h→Frank。没有升级路径的 SLA 是没有牙齿的纸老虎。 |
| 3. 用户可见判定 | 五步判定顺序：安全漏洞 → 用户可感知 → 数据完整性 → 系统健康度 → 纯主观。许清楚的第一刀在 Step 2——QA 加了两道安全网（Step 3-4），不是推翻，是防漏。 |
| 4. Bug Report 模板 | 10 字段：标题/级别/模块/环境/复现步骤/预期vs实际/复现率/附件/数据敏感度。6 个 QA 填，1 个系统预填 + QA 补充，1 个系统自动。模板的价值是让研发少问「你这是什么意思」。 |

### 许清楚 R2 让步后，QA 的剩余待办

许清楚在 3 个关键分歧上让步——QA 表示感谢。以下是让步后 QA 需要推动落地的 3 件事（不是 R2 辩论内容，是 R3 Frank 决策后的执行项）：

1. **申诉模板要写进 issue 系统的 workflow 里**，不是参考文档。申诉按钮点下去 → 系统弹出模板（不是 QA 自己找文档复制粘贴）→ QA 填写 → 系统自动 assign 给产品。
2. **SLA tracking 要从人工变系统**。QA 不能每天对着 Excel 手动计算「这个 bug 多久没人看了」。Issue 系统需要 SLA 计时功能——这是工具链需求，研发团队负责实现。
3. **Bug Report 模板要集成到 QA 提 bug 的入口**。QA 点击「新建 Bug」→ 看到的不应该是空白文本框，而是 10 字段的表单。减负，不是加负担。

### QA 对 Frank 的一句话

**R1 我说「标准要能真正用起来」——R2 四方共识让标准在纸面上完整了；现在缺的是工具链把纸面标准变成 QA 每天点一下就能走的流程。纸面标准不贵在完美，贵在有人愿意天天用。**

## 附：QA 判定顺序 checklist（给 issue 系统的 tooltip）

```
Bug 级别判定（QA 逐条走）：

□ 1. 安全漏洞？（对照 OWASP Top 10 checklist）
     → 是 → 最低 MAJOR（认证绕过/数据泄露/可远程注入 → BLOCKER）
     → 否 → 继续

□ 2. 用户可感知？（UI 异常 / 操作失败 / 体验明显退化）
     → 是 → 功能阻断+无 workaround → BLOCKER
           → 功能阻断+有 workaround → MAJOR
           → 不影响核心任务 → MINOR
     → 否 → 继续

□ 3. 数据完整性受影响？
     → 涉及 S 级数据（资金/资产/订单）→ BLOCKER
     → 涉及 A 级数据（用户基础信息/权限）→ MAJOR
     → 否 → 继续

□ 4. 系统健康度退化？
     → OOM/崩溃/错误率突增 5x+ → BLOCKER
     → 内存泄漏（预计 48h OOM）/ 错误率 2-5x → MAJOR
     → 否 → 继续

□ 5. 纯主观偏好？（代码风格/命名/重构）
     → 是 → SUGGESTION
     → 以上都不匹配 → MINOR + 标注 triage_needed

灰色地带规则：
- 两个级别都说得通 → 取高级别 + 标注 triage_needed
- 概率性 bug（涉及资金/核心功能）→ 以最坏情况定级 + 附带复现率
- 环境差异 bug → 按 production 影响定级 + 标注 env:specific
```
