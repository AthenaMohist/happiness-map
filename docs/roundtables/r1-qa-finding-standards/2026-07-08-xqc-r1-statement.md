# R1 发言：许清楚（产品）— QA 发现分级标准与处理流程

> 发言时间：2026-07-08
> 发言轮次：R1（首个发言）
> 议题类型：A（Yes/No 决策 — 标准制定）

---

## stance

**维持「4 级分层（BLOCKER / MAJOR / MINOR / SUGGESTION）」方案，不做结构性调整。** 但在判定标准和默认处理策略上需要补充细化——这是我今天发言的核心内容。

四个级别太少（2-3 级则区分度不够），太多则加重 QA 的认知负担。4 级是行业验证过的 sweet spot（Google Buganizer、Jira 默认优先级均为 4-5 级），团队 size 无关，分工效率有关。

---

## concern_level: HIGH

理由：没有统一标准会导致三个产品级风险：

1. **QA 和研发反复扯皮**——同一个问题，QA 说 blocker，研发说 minor，没有共同语言就变成消耗战。
2. **用户可见的 bug 被代码风格争议挤占排期**——优先级不透明时，响的 squeaky wheel 拿资源，而不是伤用户最深的 bug。
3. **发布决策无依据**——Frank 问"能不能发版"的时候，我们需要能说"BLOCKER=0、MAJOR≤2、均已确认不阻塞"，而不是"感觉差不多了"。

---

## specific_opinions

### 1. 分级定义与判定标准

**维持 4 级，但需要给每个级别一个"一句话定义 + 判定公式"：**

| 级别 | 一句话定义 | 判定公式 |
|------|-----------|----------|
| **BLOCKER** | 不修不能发版 | 用户可见 AND 功能阻断 AND 无 workaround |
| **MAJOR** | 严重影响体验，发版需标注 known issue | 用户可见 AND (功能阻断但有 workaround OR 体验严重退化) |
| **MINOR** | 不好但用户能忍 | 用户可见 AND 不影响核心任务完成 |
| **SUGGESTION** | 不做更好但不做也行 | 用户不可见 OR 纯主观偏好（代码风格、命名、结构优化） |

**关键区分原则**：

- **「用户可见」是第一刀**。用户看不到的问题（代码风格、内部重构建议）直接归 SUGGESTION，不参与 BLOCKER/MAJOR/MINOR 讨论。这不代表不重要，但代表不阻塞发版。
- **「workaround 是否存在」是第二刀**。用户能被临时方案解救的，从 BLOCKER 降为 MAJOR。

**具体举例**（直接回答会议提出的问题）：

| 场景 | 级别 | 理由 |
|------|:---:|------|
| 支付按钮点击无响应，无替代路径 | BLOCKER | 用户可见 + 功能阻断 + 无 workaround |
| 支付按钮点击无响应，但手动输入金额可绕过 | MAJOR | 用户可见 + 功能阻断 + 有 workaround |
| 动画卡顿 3 秒但不影响操作 | MINOR | 用户可见 + 体验退化 + 不阻断任务 |
| 变量命名 `x` 应该改成 `userCount` | SUGGESTION | 用户不可见 + 纯代码层面 |
| 按钮颜色与设计稿差 2px | 视情况 | 用户能注意到 → MINOR；需叠加对比才看出 → SUGGESTION |

**产品视角的理由**：分级不是为了给问题贴标签，而是为了让发布决策可计算。发布标准应该能写成：「BLOCKER=0 AND MAJOR≤N（N 由当前版本风险承受度决定）」。

### 2. 论证流程规则（通过 / 驳回 / 暂缓）

**不要试图让所有人同意所有事的级别。目标是「快速收敛，不阻塞」。**

#### 2.1 基础流程

```
QA 发现 → 按判定公式标注级别 → 研发评估 → 三种结果：
  ├── 通过（agree）    → 按级别默认策略处理
  ├── 驳回（reject）    → 不可申诉，直接关闭
  └── 暂缓（defer）     → 记录版本，降低优先级
```

#### 2.2 各结果的判定标准

**通过（agree）的条件**：
- 研发认为 QA 的级别标注正确 → 直接通过
- 研发认为级别合理但标准有误 → 修正级别后通过（如 BLOCKER → MAJOR）
- 研发认为级别偏高但影响不大 → 按原级别通过（不纠结）

**驳回（reject）的条件**：
- 非 bug（by design / 预期行为）→ 直接驳回，标注 `won't fix / by design`
- 无法复现（QA 提供复现步骤后研发仍无法复现）→ 驳回，标注 `cannot repro`
- SUGGESTION 级别的问题，研发判断改的成本 > 收益 → 驳回，标注 `cost > benefit`

> ⚠️ **驳回不可申诉的原则**：驳回是研发的专业判断。QA 可以追加证据后重新提交为新 issue，但不能在原 issue 上拉锯。这防止「一个 issue 讨论 3 天」的消耗。

**暂缓（defer）的条件**：
- MINOR/SUGGESTION，但当前版本排期已满 → 标记目标版本（下版本 / backlog）
- MAJOR，但有 workaround 且修复成本高 → 先发版标注 known issue，下版本修
- BLOCKER，但影响的是非主路径（冷门功能、内测用户专属）→ 需 Frank 确认后才能暂缓

> **产品红线**：BLOCKER 暂缓必须 Frank 确认。这是唯一需要第三方的场景——因为 BLOCKER 的定义是"不修不能发版"，暂缓等于推翻这个定义，需要 project owner 签字。

#### 2.3 争议升级机制

当 QA 和研发在级别认定上无法达成一致（持续 2 轮以上）：

```
争议升级 → 产品（许清楚）介入裁定
  ├── 产品看用户影响 → 用户不可见 → 降为 SUGGESTION
  ├── 产品看 workaround → 有 → 降为 MAJOR
  └── 产品看用户基数 → 影响 < 5% 用户 → 降一级
```

裁定依据始终来自用户视角，不陷入技术细节争议。

**产品视角的理由**：这个流程的设计目标是「让 90% 的问题在第一轮研发评估后直接闭环」。只有真正有争议的 10% 才需要产品介入。如果这个比例超过 30%，说明分级标准不够清晰，需要回头 refine 判定公式。

### 3. 不同级别的默认处理策略

| 级别 | 默认策略 | 是否必修 | 备注 |
|------|---------|:---:|------|
| BLOCKER | 必须修复后发版 | ✅ 必修 | 不计入排期优先级——无条件修复 |
| MAJOR | 尽量修复；若时间不够，发版标注 known issue | ⚠️ 尽力修 | 当前版本 MAJOR 上限：建议 ≤3 个 |
| MINOR | 记录 backlog，当前版本有余力则修 | ❌ 不阻塞 | 不允许 MINOR 挤占 MAJOR 修复时间 |
| SUGGESTION | 直接关闭 / backlog（研发自决） | ❌ 不阻塞 | QA 可提交但研发有权直接 close |

**关于「直接关闭」的设计意图**：SUGGESTION 级别的直接关闭是一种**信号机制**。如果研发觉得有价值（改一下又不费事），自然会修——不需要流程驱动。如果研发觉得不值，QA 不应以流程强迫。这是对研发专业判断的尊重。

**产品视角的理由**：默认策略的核心思想是——「级别越高，自由度越低」。BLOCKER 是 0 自由度（必须修），MAJOR 是低自由度（尽量修），MINOR 是高自由度（看着办），SUGGESTION 是无限自由度（自己定）。这避免了「所有问题都重要，所以所有问题都不重要」的优先级通胀。

---

### 4. SLA / 时效性

| 级别 | 响应时限（研发评估） | 修复时限（如有） |
|------|:---:|:---:|
| BLOCKER | 4 小时内 | 24 小时内修复 + 回归 |
| MAJOR | 1 个工作日内 | 当前版本窗口内 |
| MINOR | 2 个工作日内 | 不限 |
| SUGGESTION | 3 个工作日内 | 不限 |

**产品视角的理由**：

- **BLOCKER 4h 响应**：不是要求 4h 修好，而是要求 4h 内有人看了这个 issue 并给出判断。如果 QA 周五下午提了一个真正不能发版的 bug，周一才有人看，整个周末的窗口就浪费了。
- **MAJOR 1 工作日**：给研发足够的缓冲但不过度拖延。
- **MINOR/SUGGESTION 的宽松时限**：避免「紧急不重要」的事情挤占「重要不紧急」的核心工作。这是对抗「伪紧急」的防火墙。
- **修复时限 vs 响应时限**：区分响应和修复——先确认，后修复。不要求 BLOCKER 24h 修好（可能真的有很难修的问题），但要求 24h 内有方案（修 / workaround / 确认暂缓需 Frank 签字）。

**补充——跨时区的 Slack 规则**：如果 BLOCKER 在非工作时间提交，响应时限从下一个工作时段开始时计算。不要求 24/7 值守——这是纪律，不是虐待。

---

## 总结

我的发言可以浓缩为四句话：

1. **4 级分层不改**，但给每个级别一个「判定公式」让 QA 和研发有共同语言。
2. **驳回不可申诉**——研发专业判断，QA 追加证据重新提交，不在原 issue 上拉锯。
3. **BLOCKER 暂缓必须 Frank 签字**——这是唯一的产品红线。
4. **SLA 区分响应和修复**——先确认，后修复，不混为一谈。
