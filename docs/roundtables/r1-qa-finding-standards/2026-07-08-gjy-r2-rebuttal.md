## 分歧 1：驳回机制 —「有成本申诉」落地

### 立场：坚持「有成本申诉」，给出完整落地流程

许清楚尚未就驳回机制表态（R1 等待回应中），但寇豆码和 QA 均已明确支持「有成本申诉」方案。3/4 已达成共识。

**具体操作流程（落地版）：**

```
研发驳回 issue
  ├── 必须附带驳回理由（by design / cannot repro / cost > benefit / level downgrade）
  └── QA 收到驳回后：
        ├── 接受 → issue 关闭
        └── 申诉 → issue 标记 status:appeal
              ├── QA 必须附带：新复现证据 OR 新影响面分析 OR 新用户反馈
              │   （空手申诉不被受理——issue 系统层面校验：appeal 状态下必须有附件或新增评论 ≥ 200 字）
              ├── 申诉由产品（许清楚）直接裁定，跳过二轮研发
              │   └── 为什么跳过二轮？研发已经在这个 issue 上表过态了，再问一次大概率同答案
              ├── 产品裁定依据：用户影响面、业务风险、成本收益
              └── 产品裁定为最终，不可再申诉（防止三方拉锯）
```

**「谁来判断新证据是否足够？」**

产品（许清楚）。不是技术判断——是流程判断：QA 是否提供了「之前没有的新信息」。如果 QA 只是把原 issue 重说一遍，产品可以直接驳回申诉。如果 QA 提供了新的复现录屏、新的影响面数据、新的用户投诉——产品裁定争议 issue 的级别。

这个设计不要求产品懂技术——产品只需要回答两个问题：
1. QA 这次说的东西和上次有本质区别吗？（有 → 值得重新看）
2. 从用户角度看，这个 bug 什么级别？（回到判定公式）

**如果许清楚坚持「驳回不可申诉」——我的最大妥协：**

不接受「驳回不可申诉」本身。但可以接受的妥协方案是：

> **「驳回冻结期 + 重新提交引用链」**
> - 驳回后原 issue 冻结 48h（防止即时拉锯）
> - QA 可以在 48h 后重新提交为新 issue，但必须用系统字段 `supersedes: #原issue号` 建立追溯链
> - 重新提交时仍适用正常评估流程（不跳过研发）
> - 同一个 bug 最多重新提交 1 次（之后不可再提）

**但与我的方案比，这个妥协方案更差**——追踪链不如同 issue 干净、额外消耗 issue 号、统计污染（寇豆码已指出）。我提交这个妥协方案只是为了证明：我不是在坚持「必须按我的来」，而是在坚持「必须有追索路径」。许清楚的「驳回不可申诉 + 重新提交」是追索路径吗？不算——因为两个独立 issue 之间没有系统级的因果链。

**一句话理由**：3/4 的人支持有成本申诉，包括被驳回最多的 QA 和被申诉最多的研发——这个方案对双方都是最优解。

## 分歧 2：SLA 定位时限 —「8h 根因定位」vs「初步判定+进度同步」

### 立场：让一步，接受「初步判定+进度同步」的标签，保留 8h 时限和内容要求

寇豆码的论点是诚实的：跨系统级联故障、竞态 bug、数据依赖型 bug——这些场景下 8h 完成根因定位确实不现实。QA 也支持这个判断。作为不做日常 debug 的架构师，我接受这个来自一线的反馈。

**修正后的三档 SLA（架构最终版）：**

| 级别 | 响应时限 | 定位/判定时限 | 方案时限 |
|------|:---:|:---:|:---:|
| BLOCKER | 4h | 8h（初步判定） | 24h |
| MAJOR | 1 工作日 | 2 工作日 | 当前版本窗口内 |
| MINOR | 2 工作日 | — | 不限 |
| SUGGESTION | 3 工作日 | — | 不限 |

**8h 初步判定必须产出的内容（不变——只是标签从「根因定位」改为「初步判定」）：**

1. 问题涉及哪些系统/模块？
2. 已排除哪些假设？当前排查方向是什么？
3. 是否需要跨团队协调？需要找谁？
4. 预计还需要多少时间完成根因定位？
5. 如果已定位根因——直接进入方案阶段（提前完成不违规）

**如果 8h 仍无法完成初步判定（排查方向都不明确）：**
- 研发主动升 flag → 产品做 stakeholder 沟通
- Frank 决策：继续等定位还是暂缓发版
- 这不记为 SLA 违约——记为「复杂 bug 的已知风险 materialized」

**关键设计意图**：把「根因定位」改为「初步判定」不是降低标准——是让标准不撒谎。原先的「8h 根因定位」在 50%+ 的跨系统 bug 上会违约，一个频繁被违反的 SLA 比没有 SLA 更危险（信用破产）。现在的「8h 初步判定」是可执行、可验证的：8h 到了，你有没有产出上述 5 项内容？有 → SLA 达标；没有 → SLA 违约。

**一句话理由**：寇豆码作为每天 debug 的人说 8h 根因定位不现实——我相信他。但 8h 的时限不撤，只是交付物从「根因」变为「初步判定」。

## 分歧 3：安全漏洞独立判定 — 边界定义

### 立场：坚持安全漏洞独立判定，明确判定边界

QA 支持我的方向，但要求补充 PII 隐私数据按安全漏洞处理，并要求明确边界。以下是我的边界定义：

**安全漏洞的判定边界（三层）：**

### 第一层：明确属于安全漏洞（进入前置检查，最低 MAJOR）

| 类别 | 具体内容 | 依据 |
|------|---------|------|
| **OWASP Top 10 大类** | SQL 注入、XSS、认证绕过、敏感信息泄露、CSRF、SSRF、不安全反序列化、访问控制缺陷、安全配置错误、日志/监控不足导致无法检测攻击 | 行业标准。不要求完整 list——OWASP Top 10 是 baseline。 |
| **PII 隐私数据泄露** | 日志/API 响应/前端暴露中的手机号、身份证、银行卡号、家庭地址、生物特征（QA 补充，我完全接受） | 个保法/GDPR 合规风险。即使概率极低，合规风险等同安全漏洞。 |
| **数据泄露（非 PII 但敏感）** | 业务机密数据（订单金额、合同条款）被越权访问 | 商业风险。非合规风险但影响等同。 |

> **一句话规则**：凡是涉及「未授权的数据访问 / 数据泄露 / 权限绕过」的，不管用户是否「看到」了异常——直接进入安全漏洞前置检查。

### 第二层：有条件算（需要 CVSS 评分或等效判断）

| 类别 | 判定条件 |
|------|---------|
| **CVE 漏洞（依赖/框架层面）** | CVSS ≥ 7.0 → 等同于 BLOCKER 级安全漏洞；CVSS 4.0-6.9 → 等同于 MAJOR 级；CVSS < 4.0 → 按正常公式判定。**不需要 CVE 编号才判定——有等效风险即可。** |
| **基础设施安全** | 容器逃逸、K8s RBAC 配置缺陷、未加密的内部通信 → 即使不暴露公网，也按安全漏洞判定。理由：内部系统被攻破后横向移动的风险是真实存在的。 |

### 第三层：不算安全漏洞（按正常公式判定）

| 场景 | 判定 | 理由 |
|------|:---:|------|
| 内部管理后台的 UI bug（非权限相关） | 按正常公式 | 不影响安全边界 |
| 「用户可能猜到另一个用户的 ID」但后端有权限校验 | 按正常公式（但需研发验证权限校验确实有效） | 有纵深防御即可 |
| 纯理论攻击（需要物理接触服务器） | 按正常公式 | 攻击面不暴露 |

**关于「内部系统、不暴露公网」的漏洞：**

算。内部系统不等于没有威胁。内部威胁（恶意员工、钓鱼后横向移动）是真实攻击面。OWASP 明确要求纵深防御——「不暴露公网」是一个防御层，但不是豁免安全标准的理由。判定时按「如果这个漏洞被利用了的损害程度」定级，不按「当前暴露面大小」打折。

但如果内部系统的 bug 修复窗口可以放宽（不影响外部用户），这不改变级别——改变的是 SLA 时限（可以放宽，类似我的第三方依赖 SLA 放宽逻辑）。

**一句话理由**：安全漏洞的边界 = OWASP Top 10 + PII 泄露 + CVSS ≥ 4.0 + 内部横向移动风险。口诀：有权限绕过 or 数据泄露 or PII 暴露 → 就是安全漏洞，不管用户看不看得见。

## 分歧 4：架构风险维度落地优先级

### 立场：10 个维度合并为 7 个，分 P0/P1 两档

我提出的 5 个维度 + 寇豆码提出的 5 个维度，存在重叠可合并。合并后的完整维度清单及优先级：

### P0：必须立刻写入标准（6 个维度）

| # | 维度 | 来源 | 合并说明 |
|---|------|------|---------|
| **1** | **回归范围声明（Blast Radius）** | 高见远 | BLOCKER/MAJOR 修复必须附带最小回归范围（修复模块 + 1 级依赖）。QA 执行定向回归。**与寇豆码的「修复发布门禁」合并**——回归范围声明是发布门禁的前提（不知道范围怎么 smoke test？）。 |
| **2** | **修复发布门禁** | 寇豆码 + 高见远（合并） | BLOCKER：强制 code review + staging smoke test（QA 执行）+ 灰度发布（如有能力）。MAJOR：推荐 review + staging 回归。这是「回归范围声明」的下游动作。 |
| **3** | **Schema/API 变更强制影响面评估** | 高见远 | BLOCKER/MAJOR 修复涉及 schema 变更、API breaking change 时，必须列出所有受影响消费者并确认兼容策略。这是不可跳过的架构步骤。 |
| **4** | **可复现性门禁** | 寇豆码 + QA（合并修正） | QA 提交 BLOCKER/MAJOR 时必须附带复现步骤 + 环境信息 + 复现率。研发驳回「cannot repro」时必须附带自己的复现尝试次数和所用环境。**采用 QA 的修正版**：区分「无证据」和「难复现」，仅前者可降级。 |
| **5** | **跨团队 SLA handoff** | 寇豆码 | 经研发判定需跨团队时，被调方独立起算响应时限（BLOCKER 级别也是 4h）。无法按时响应时升 flag。缺失这条，BLOCKER 的端到端 SLA 在微服务架构中是假的。 |
| **6** | **环境差异处理** | 寇豆码 + QA（合并修正） | Bug 级别按 production 影响定级，不因环境降级（QA 立场）。研发需要 staging 调试权限/脱敏数据时 SLA 暂停等待（寇豆码立场）。环境差异不作为驳回理由——仅作为 SLA 暂停理由（QA + 寇豆码共识）。 |

### P1：记入标准附录，后续迭代（4 个维度）

| # | 维度 | 来源 | 理由 |
|---|------|------|------|
| **7** | **Bug Pattern Detection（模块级架构腐化信号）** | 高见远 | 需要 issue 系统支持「所属模块」required field + 自动化 Dashboard（寇豆码已指出）。工具链就绪前靠人工统计不可靠。先写进标准作为「目标」，工具补齐后切换为「规则」。 |
| **8** | **第三方依赖 SLA 放宽** | 高见远 | 涉及第三方 SDK/API 的 BLOCKER 方案时限放宽至 48h。这个是 important 但不是 urgent——团队当前依赖面我不清楚，写了用不上不如先记下。 |
| **9** | **可观测性退化监控** | 高见远 | 修复涉及移除/修改埋点时注明。由架构师抽查，不阻塞发版。这个不需要流程强制——记入架构治理 checklist 即可。QA 补充的 `observability_gap` 标签是这个维度的数据输入。 |
| **10** | **技术债务追踪工具化** | 寇豆码 | 模块级 bug 密度 Dashboard、per-module `cannot_repro` 驳回率、`observability_gap` 标签密度。这些需要工具链先就绪——先记入标准附录作为「需要的工具能力」。 |

### 合并后的去重结果

| 原始维度 | 去向 |
|---------|------|
| 高见远：回归范围 | → P0 #1（与寇豆码「发布门禁」合并） |
| 寇豆码：发布门禁 | → P0 #2（合并后） |
| 高见远：Pattern Detection | → P1 #7 |
| 高见远：Schema 变更评审 | → P0 #3（独立保留——不可合并） |

| 高见远：可观测性退化 | → P1 #9 |

| 寇豆码：环境差异 | → P0 #6（与 QA 修正合并） |

**一句话理由**：P0 = 没有这个，SLA 会在真实场景中系统性违约。P1 = 重要但不阻塞发版，工具补齐后自然生效。

## 总结

| 分歧 | 立场 | 让步条件 | 理由 |
|------|:---:|------|------|
| 1. 驳回机制 | **坚持**「有成本申诉」 | 许清楚若坚持，最大妥协为「冻结期 + 追溯链」，但不接受完全不可申诉 | 3/4 已共识。研发和 QA 双向确认这是最优方案 |
| 2. SLA 定位时限 | **让步**：接受「初步判定+进度同步」替代「根因定位」 | — | 来自一线的反馈：跨系统 bug 根因确实不是 8h 能搞定的。标签改了，时限和内容要求不变 |
| 3. 安全漏洞边界 | **坚持**独立判定，给出三层边界定义 | — | 边界已明确：OWASP Top 10 + PII + CVSS≥4.0 + 内部横向移动风险。边界清晰才能执行 |
| 4. 风险维度优先级 | **与寇豆码合并**维度，10→7，P0/P1 分档 | — | P0 是「没有就违约」的 6 个维度。P1 是「工具就绪后自然生效」的 4 个维度 |

**对许清楚 R1 框架的最终评价**：骨架正确、产品逻辑自洽——经四轮交叉辩论后，修正版判定公式已覆盖安全/性能/数据/可复现性/环境差异五个原框架的盲区，SLA 从「表格与文字自相矛盾」变为「响应/判定/方案」三档可执行结构，驳回机制从「单向关闭」变为「有成本的追索路径」。这套标准现在可以落地了。
