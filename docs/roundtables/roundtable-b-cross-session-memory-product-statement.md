# Roundtable B: 产品发言 — 跨会话记忆与知识传递优化

> 角色：许清楚（产品负责人） | 日期：2026-07-24
> 类型：Brainstorming — 从用户痛点和需求优先级出发
> 背景：Frank 与 OC 在飞书聊天，每次 100M token 上限耗尽后切新会话，OC 遗忘所有历史

---

## 问题 1：这个用户痛点有多大？（量化 Frank 的实际困扰）

### 1.1 时间浪费估算

从 session 历史分析，OC 与 Frank 的对话是高强度协作——单次会话 500-1000+ 条消息，内容涵盖需求讨论、代码审查、bug 排查、架构决策。每次切换会话后 OC "归零"，Frank 必须：

| 浪费类型 | 单次成本 | 触发频率 | 月浪费估算 |
|---------|:---:|:---:|:---:|
| **重新解释已被纠正的问题** | 10-30 min | 每次涉及跨会话的议题 | 2-6h/月 |
| **OC 重新调查已知结论** | OC 自转 2-5 轮 | 每次提及历史决策 | 不可见但消耗 token 配额 |
| **Frank 回忆"上次怎么说的"** | 5-10 min | 每次纠正 OC | 1-3h/月 |
| **重复踩坑**（梦见报告投递是典型案例） | 15-30 min/次 | 活跃项目每周 1-2 次 | 4-8h/月 |

**保守估计：每月 Frank 有 7-17 小时浪费在"教 OC 它已经学过的东西"上。**

### 1.2 典型案例：做梦报告投递问题

| 日期 | 事件 | Frank 投入 |
|------|------|:---:|
| 7/12 | 第一次纠正：做梦报告投递方式不对，Frank 指出正确方式 | ~20 min |
| 7/15 | 第二次纠正：OC 又忘了，Frank 重申并要求备份投递方式 | ~15 min |
| 7/21 | 第三次纠正：OC 再次遗忘，Frank 强行让照抄 backup 的投递方式 | ~30 min |
| 7/24（今天） | 新会话 OC 仍然一无所知，要重新排查、重新研究方案 | **待发生** |

> 同一问题被纠正 3 次，但跨会话后依然归零。要不是 Frank 强行让照抄 backup，今天又要重踩旧坑。这个案例不是孤例——它是结构性问题的缩影。

### 1.3 恶化因素

- **静默超时自动切会话**：每天至少发生一次，不是 Frank 主动切的——是系统被动切的。这意味着 OC 的"失忆"是**定时发生的、不可预期的**。
- **token 配额压力**：100M 上限意味着 Frank 不敢在同一个会话里放太多上下文，被迫"节约用 token"→ 加速切换频率。
- **复合效应**：纠正 × 遗忘 × 重新纠正 → 每次都比上一次更费 token（历史包袱越来越重）。

## 问题 2：期望的体验是什么？（理想状态下跨会话应该记住什么？）

OC 作为 Frank 的"AI 队友"（SOUL.md 原话），跨会话应该像一个**不会失忆的同事**——今天来上班，应该知道昨天做到哪了、什么被否决过、什么被纠正过。

### 2.1 记忆分层模型

| 层级 | 记住什么 | 时效性 | 例子 |
|:---:|------|:---:|------|
| **L1 上下文** | 当前任务的进度和状态 | 任务周期内 | "做梦报告 cron 我们讨论到方案 C，上次决定用 backup 的投递方式照抄" |
| **L2 决策** | Frank 已做出的决策和纠正 | 永久或主动废止 | "做梦报告投递不要用 X 方式，必须用 Y 方式——Frank 纠正过 3 次了" |
| **L3 偏好** | Frank 的习惯、风格、红线 | 长期 | "Frank 不喜欢被问'你确定吗'，直接说结论" |
| **L4 知识** | 项目中积累的技术认知 | 项目周期 | "watchdog v4 的 session file 协议是什么样的" |

### 2.2 理想的新会话启动流程

```
OC 启动 → 
1. [自动] 读取最近 N 个会话的摘要（关键决策 + 当前任务状态）
2. [自动] 检查 memory/skills 中是否有相关纠正记录
3. [自动] 检查 kanban 中是否有进行中的任务
4. [主动告知 Frank] "我恢复了上次的上下文：我们在做 X，上次你纠正了 Y，当前 Z 任务还在进行中。继续？"
```

**关键设计原则：OC 主动恢复，不要让 Frank 提醒 OC 去查。**

### 2.3 什么不应该跨会话记住

- 单次会话的中间推理过程（token 浪费）
- 已完成的临时操作序列
- 误判后被 Frank 明确否定的思路（除非标记为"已否决"以供参考）

## 问题 3：最痛的必须优先解决的是什么？（优先级排序）

### 3.1 优先级矩阵

我按「用户痛苦 × 解决难度」二维评估：

```
高痛苦 │  P0: 纠正遗忘        │  P1: 任务上下文断点
       │  (OC 不记得被纠       │  (新会话不知道做到哪了)
       │   正过的行为)         │
       │                      │
低痛苦 │  P2: 长期知识积累     │  P3: 会话间推理延续
       │  (项目技术认知)       │  (上一个会话的思考链)
       └──────────────────────┴─────────────────────
         低难度                  高难度
```

### 3.2 P0（必须立刻解决）：纠正遗忘 — "OC 不主动用 session_search"

这是**最大的痛苦 × 最低的解决成本**。

**现状**：session_search 工具可用，但 OC 不主动在会话开始时调用。PIPELINE.md 有跨会话续接规范，但那是针对 OC 自己主动发起的续接（kanban 任务接力），不是针对"Frank 在飞书找 OC 聊天"的被动场景。

**最小可行方案**：OC SOUL.md 增加一条铁律——

```
铁律 6：跨会话启动协议
每个新会话开始的前 3 轮内，必须：
1. 调用 session_search 查询「最近 3 天内与 Frank 的关键决策和纠正」
2. 检查 memory 中的活跃事实
3. 向 Frank 确认上下文：'上次我们讨论到 X，你纠正过 Y。继续还是新话题？'
```

**改动量**：OC SOUL.md 加 ~10 行规则。零代码。
**预期效果**：消除 70% 的纠正遗忘问题（覆盖"上次你说过…"类场景）。

### 3.3 P1（本周解决）：任务上下文断点 — 强化 kanban + memory 联动

**现状**：PIPELINE.md 有 `.oc_relay.json` 接力协议，但它只覆盖 OC 主动发起的任务接力。飞书 DM 场景下 OC 不会自觉读这些文件。

**方案**：
- 每次 Frank 纠正 OC 的行为/决策 → OC 必须写入 memory（不用等 Frank 说"记住这个"）
- 写入 memory 的内容模板：`[纠正] {话题}：Frank 要求 {正确做法}，不要 {错误做法}。日期：{date}。关联上下文：{session_id}`
- 新会话启动 → 自动 load memory → 发现带 `[纠正]` 标签的 → 主动确认

**改动量**：OC SOUL.md 加纠正记录规则（~5 行）+ memory 工具的自动读取规则（~3 行）。
**覆盖范围**：纠正类遗忘 + 偏好类遗忘。

### 3.4 P2（下个迭代）：跨会话摘要 — "今天之前发生了什么"

**方案**：每次 OC 会话接近 token 上限或主动结束时，自动生成一个结构化摘要写入 memory：

```yaml
session_id: 20260724_xxx
date: 2026-07-24
key_decisions:
  - "做梦报告投递：确认使用 backup 的投递方式，不要重新发明"
  - "watchdog v4: 确认三态状态机方案，开始编码"
corrections:
  - "Frank 纠正：report 格式去掉 emoji，用纯文本"
active_tasks:
  - "t_e78de385: 跨会话记忆优化（当前）"
```

新会话启动 → OC 读取最近摘要 → 5 秒内恢复上下文。

**改动量**：需要新增摘要生成逻辑（LLM prompt）+ memory 写入。

### 3.5 不做什么（现阶段）

| 方案 | 为什么不现在做 |
|------|--------------|
| **Mem0 语义搜索增强** | Mem0 已可用，核心问题是 OC 不主动调用——先把调用习惯建立起来，再考虑升级搜索能力 |
| **全量会话回放** | token 杀手。OC 已经 100M 不够用了，回放历史会让问题更严重 |
| **向量化所有决策** | 过度工程。当前数据量（数百条决策）不需要 embedding，关键词匹配 + 时间排序够用 |
| **修改 Hermes 引擎层** | 不必要。问题不在引擎，在 agent 行为规则 |

---

## 总结：三句话说清楚

1. **痛点真实且量化**：Frank 每月 7-17 小时浪费在重复教 OC 已学过的东西，做梦报告同一问题被纠正 3 次仍未跨会话记住。
2. **理想态清晰**：OC 新会话启动时像不会失忆的同事——自动恢复上次上下文、主动告知 Frank 而不是等 Frank 提醒。
3. **最优先的是 P0**：OC 不主动用 session_search 是最大浪费——改 SOUL.md 加一条铁律（零代码），OC 每个新会话前三轮内必须查历史、对上下文。这个改动能消除 70% 的纠正遗忘问题。
