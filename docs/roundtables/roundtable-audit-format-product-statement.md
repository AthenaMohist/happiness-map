## 1. Agent 使用场景全景（需求侧）

审计数据不是给人看的，是给 agent 查的。以下列举我能想到的所有 agent 查询场景，按频率和价值排序：

### 第一层：即时诊断（高频，强需求）

| 场景 | Agent 问什么 | 频次 |
|------|-------------|:---:|
| **S1 会话复盘** | "session X 里执行了哪些命令？什么顺序？哪个失败了？" | 每次异常 session |
| **S2 命令溯源** | "这条错误命令之前执行了什么？上下文是什么？" | 每次排查 |
| **S3 输出回溯** | "执行 `pip install foo` 的时候终端输出了什么？" | 日常 debug |

### 第二层：统计洞察（中频，运营决策）

| 场景 | Agent 问什么 | 频次 |
|------|-------------|:---:|
| **S4 失败排行榜** | "最近一周失败率最高的 10 个命令是什么？" | 每日/每周 |
| **S5 趋势告警** | "`git push` 的失败率从 2% 飙升到 15%，什么时候开始的？" | 异常触发 |
| **S6 会话健康度** | "过去 24h 有多少 session 错误率 > 30%？" | 运维看板 |
| **S7 性能回归** | "某个命令的执行频率/失败率是否突然变化？" | 部署后验证 |

### 第三层：行为挖掘（低频，产品迭代）

| 场景 | Agent 问什么 | 频次 |
|------|-------------|:---:|
| **S8 工作流挖掘** | "game-engine 在修 bug 时的典型命令序列是什么？" | 月度/按需 |
| **S9 能力画像** | "orchestrator 最常失败的是哪类命令？网络？文件？权限？" | 季度审计 |
| **S10 安全审计** | "过去 7 天有没有执行过 `rm -rf /` 或 `curl | bash`？" | 按需 |
| **S11 合规追溯** | "task t_xxx 执行期间的所有终端操作记录在哪里？" | 按需 |

### 第四层：智能辅助（远期，理想态）

| 场景 | Agent 问什么 | 频次 |
|------|-------------|:---:|
| **S12 预测建议** | "当前 context 类似 session Y，下一步通常执行什么？" | 实时 |
| **S13 异常检测** | "这个命令序列和正常模式显著不同，可能是个 bug 或攻击" | 实时 |
| **S14 成本归因** | "上周 token 消耗最高的 5 个 session 各执行了多少命令？" | 周报 |

## 2. 什么格式/能力对 agent 最有价值

Agent 不像人类需要可视化界面。Agent 需要的是：**可组合的查询原语** + **足够丰富的字段**。

### 2.1 必须有的查询能力（缺了就是残废）

| 能力 | 用户故事 |
|------|---------|
| **时序过滤** | "最近 2 小时的" / "2026-07-10 全天的" |
| **会话隔离** | "只看 session X 的" |
| **状态过滤** | "只看失败的命令" (exit_code != 0) |
| **命令匹配** | "命令中包含 `pip install` 的" |
| **聚合统计** | "按命令分组统计失败率" |
| **聚合窗口** | "按天/按小时统计命令量" |

### 2.2 强烈想要的查询能力（当前缺失会造成痛点）

| 能力 | 用户故事 | 当前状态 |
|------|---------|:---:|
| **全文搜索输出** | "输出内容中包含 `Connection refused` 的命令" | ❌ 无 FTS 索引 |
| **命令序列分析** | "`git commit` 之前执行了什么？之后执行了什么？" | ❌ 需自 JOIN |
| **执行耗时** | "哪些命令耗时超过 30 秒？" | ❌ 无 duration 字段 |
| **多维度关联** | "task t_xxx → 对应哪个 session → 执行了哪些命令" | ❌ 缺 task_id 映射 |

### 2.3 远期愿景（不要求现在就做，但要留扩展空间）

| 能力 | 用户故事 |
|------|---------|
| **语义相似** | "找出和这个命令行为相似的命令"（embedding） |
| **异常基线** | "这个 session 的命令模式偏离正常多少标准差" |
| **跨域关联** | "token 消耗 + 命令执行 + 最终任务成功率 三者之间的关系" |

## 3. 当前 SQLite 扁平表能力评估

**当前 schema**：`id | message_id | session_id | timestamp | command | exit_code | output_preview | transcribed_at`

**当前数据量**：4,388 条命令，302 个会话，3,910 个唯一命令。日增 200-500 条。`output_preview` 中位数在 100-500 字符。

### 3.1 能满足的场景

| 场景 | 满足程度 | 说明 |
|------|:---:|------|
| S1 会话复盘 | ✅ 满足 | `WHERE session_id=? ORDER BY timestamp` |
| S2 命令溯源 | ✅ 满足 | 同一 session 内按时间回溯 |
| S3 输出回溯 | ⚠️ 部分 | `output_preview` 被截断，只能看摘要 |
| S4 失败排行榜 | ✅ 满足 | `GROUP BY command HAVING exit_code != 0` |
| S5 趋势告警 | ✅ 满足 | 按天/小时 GROUP BY + 聚合 |
| S6 会话健康度 | ✅ 满足 | `GROUP BY session_id` 计算错误率 |
| S7 性能回归 | ⚠️ 部分 | 可以统计频率变化，但无 duration 无法分析性能 |
| S8 工作流挖掘 | ❌ 不足 | 扁平表无序列关系，自 JOIN 笨重且非直觉 |
| S9 能力画像 | ⚠️ 部分 | 可以按命令聚类，但无法区分 agent profile |
| S10 安全审计 | ⚠️ 部分 | 可以搜索已知危险命令，但无法检测未知异常 |
| S11 合规追溯 | ❌ 不足 | 缺少 task_id → session_id 映射 |
| S12 预测建议 | ❌ 不足 | 需要序列建模 |
| S13 异常检测 | ❌ 不足 | 需要基线 + 统计模型 |
| S14 成本归因 | ❌ 不足 | 无 token 消耗字段 |

### 3.2 当前格式的核心缺口（按紧迫度排序）

| 优先级 | 缺口 | 影响场景 | 加一个字段/索引就能解决？ |
|:---:|------|---------|:---:|
| **P0** | `duration`（命令耗时） | S7 性能回归、S3 输出回溯决策（是否超时） | ✅ 加列 |
| **P0** | `output_preview` 无 FTS 索引 | S1-S3 无法全文搜索输出 | ✅ 加 FTS5 虚拟表 |
| **P1** | `task_id` 映射 | S11 合规追溯、S6 健康度 | ✅ 加列（来自 session 元数据） |
| **P1** | `profile` / `agent_id` | S9 能力画像、S8 工作流挖掘 | ✅ 加列（可从 session_id 前缀推断） |
| **P2** | 命令序列关系 | S8 工作流、S12 预测 | ❌ 需图/窗口结构 |
| **P2** | 语义搜索 | S10 安全审计、S13 异常 | ❌ 需 embedding |
| **P3** | 跨域关联（token 等） | S14 成本归因 | ❌ 需跨系统 JOIN |

## 4. 产品立场：格式不换，列要加

### 核心判断

**当前 SQLite 扁平表不是格式问题，是字段不够的问题。**

- SQLite 本身已经是 agent 友好格式：SQL 查询原语完备、零依赖、可嵌入、可被任意语言读取
- 换格式（JSON/Parquet/图数据库）解决不了当前的实际缺口——缺的是数据维度，不是存储引擎
- 增量成本极低：加一个字段 + 一个索引，现有 cron pipeline 不受影响

### 最小可行增量（建议本次窗口完成）

```
commands 表加 3 列 + 1 个 FTS 索引：

1. duration_ms INTEGER    — 执行耗时（从 bash HISTTIMEFORMAT 或 time 包装器获取）
2. task_id TEXT           — 关联的 kanban task（从 session 元数据/文件名映射）
3. agent_profile TEXT     — 执行者 profile（从 session_id 前缀或文件路径提取）
4. FTS5 索引（command + output_preview）— 全文搜索

总改动量：ALTER TABLE × 3 + 一个 FTS5 虚拟表 + cron 采集脚本补字段
```

### P0/P1 场景覆盖率提升

| 新增能力 | 解锁场景 |
|---------|---------|
| `duration_ms` | S7 性能回归：`SELECT command, AVG(duration_ms) WHERE exit_code=0` |
| `task_id` | S11 合规追溯：`WHERE task_id='t_xxx'` |
| `agent_profile` | S9 能力画像：`GROUP BY agent_profile, command` |
| FTS 索引 | S1-S3：`WHERE output_preview MATCH 'Connection refused'` |

**覆盖率从当前的 9/14（64%）提升到 12/14（86%）。**

S8/S12/S13（序列、预测、异常检测）留到下一阶段，这些需要结构变化（图/窗口），不是加字段能解决的。

### 不做的理由

- **不换格式**：SQLite 扁平表+索引就是 agent 最佳查询格式。图数据库（Neo4j）对序列分析更友好，但当前数据量和场景不值得引入新依赖
- **不加 embedding**：语义搜索有远期价值，但当前 FTS 全文搜索覆盖 80% 的搜索需求，embedding 优先度 P2
- **不引入时序列数据库**：4,388 条数据用不到 InfluxDB/TimescaleDB，SQLite 的时间范围查询已经够快

---

## 5. 总结

> 审计数据的价值不在于存储格式，在于查询维度。当前 SQLite 扁平表能用，但缺三个关键字段 + 一个 FTS 索引。加上之后能做到"agent 想查什么就能查到什么"——这才是产品意义上的价值最大化。

| 决策 | 结论 |
|------|------|
| 存储格式 | **维持 SQLite**，不换引擎 |
| P0 立即加 | `duration_ms` + FTS5 全文索引 |
| P1 本次窗口加 | `task_id` + `agent_profile` |
| P2 下阶段 | 命令序列关系、语义搜索、跨域关联 |
| 不做的 | 图数据库、embedding、时序数据库 |
