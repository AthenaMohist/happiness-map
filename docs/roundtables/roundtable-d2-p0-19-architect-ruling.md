## 议题 1: 分级合理性 — 1 MAJOR + 5 MINOR 是否合理？

### 裁定：合理。无需调整。

### 1.1 R-R3/R-R7 合并为 1 个 MAJOR — 架构层面确认

**合并理由在架构层面成立**：

- **同一根因**：LLM 概率性遗忘 relay_update.py 调用。R-R3（LLM 忘记调用）和 R-R7（SOUL.md 规则 ≠ LLM 行为）描述的是同一个故障模式在两个维度的投影——前者是表象（调用缺失），后者是机制（why 会缺失）。
- **同一故障路径**：两种表述最终都指向同一个架构事实——collector 的 `read_relay_state()` 返回 `(None, None)`，导致 watchdog 播报缺失 relay 行。
- **不可分治**：不存在一种修复只解决 R-R3 而不解决 R-R7，或反过来。stage -1/0 强制前置同时覆盖两者。

**MAJOR 判定对照**（yaml §1.2）：

```
用户可感知=是 (Frank 看不到接力状态行)
AND 体验严重退化 (OC 接力过程对 Frank 变为黑盒，违反方案 C 核心设计目标)
→ MAJOR ✅
```

**为什么不是 BLOCKER — 架构视角**：

- 核心功能（kanban 四维统计 + session 摘要）正常运行。relay 信息是一个"附加可见性层"，缺失时系统仍然功能完整。
- 不涉及 §1 中 BLOCKER 的任何触发条件：无安全漏洞、无数据一致性问题、无 OOM/crash、无 S 级数据、无资金相关概率性 bug。
- **架构层面的事实**：方案 C 的核心价值是"统一播报"（消除重复 kanban 扫描 + 统一消息格式），这个核心价值不依赖 relay 行。relay 行是增强体验，不是核心功能。

### 1.2 R-R5 降为 MINOR — 架构层面确认

**降级理由成立**：

- PATH 风险本质上是一个**部署/运维问题**，不是架构问题。架构设计（SOUL.md 定义 RELAY_HELPER 绝对路径 → relay_update.py）是正确的。
- 实测 6/6 套件绝对路径可达，证明当前部署环境下 PATH 风险已被消除。
- 如果未来部署环境变化导致绝对路径失效，那是部署问题（需调整 RELAY_HELPER 变量），不是 relay_update.py 的架构缺陷。

**判定**：R-R5 降为 MINOR 合理。PATH 是运维关注点，不是架构风险。

### 1.3 5 个 MINOR — 架构层面逐项确认

| ID | 风险 | 架构评估 | 结构性缓释 |
|----|------|---------|----------|
| R-R1 | 并发写冲突 | MINOR 正确。独立文件 + 原子写（write .tmp → os.rename）是解决并发写的标准 POSIX 模式。无锁设计在此场景下是正确的——两个 cron 偶尔同 tick 写同一文件时，最后写入者胜出，不产生半写文件。 | 原子 rename |
| R-R2 | 读取时瞬态 rename | MINOR 正确。collector 对 relay 文件做 best-effort 读取——文件不存在/不可读时不崩溃。瞬态 miss 的下个 tick（30s 后）自动恢复。这是经典的"容忍瞬态错误"模式。 | 下个 tick 自动恢复 |
| R-R4 | OC 结束 relay 残留 | MINOR 正确。SOUL.md 含清理规则。G-T1 staleness guard（10 分钟超时）作为第二道防线——即使清理规则失效，过期 relay 不会被展示。**双层防护，架构上已足够。** | SOUL.md 清理规则 + staleness guard |
| R-R5 | PATH（降级后） | MINOR 正确。见 1.2。 | 绝对路径 6/6 可达 |
| R-R6 | phase 枚举扩展 | MINOR 正确。**这正是架构层面的刻意设计——collector 透传 phase 值，不做枚举验证。** 这是松耦合：未来新增 phase 枚举值时，collector 零改动。代价是 collector 不知道 phase 是否合法，但这不是 collector 的职责——relay_update.py 的 phase 白名单已经在写入端做了校验（TC-R1-06）。 | collector 透传 + relay_update.py 白名单 |

**架构层面无遗漏**：所有 5 项 MINOR 对应的结构性缓释都在正确的架构层实现（文件层、读取层、写入层各司其职）。

## 议题 2: 处置决策 — 是否存在架构层面的隐患？

### 裁定：处置正确。存在 1 项可接受的架构风险，已通过观察期 + 升级条件覆盖。

### 2.1 MAJOR (R-R3/R-R7): 验收期观察 — 架构层面确认

**观察期的架构依据**：

当前架构的核心约束是：OC orchestrator 是 LLM agent。LLM 行为的概率性是不可消除的系统特性，不是可修复的 bug。

D1 fix 的架构策略是正确的：
```
风险降低策略：概率压缩，非概率消除
├── 阶段 -1/0 强制前置  → 降低遗忘概率（从"可能"到"极不可能"）
├── ⚠️ 铁律语言         → 提升 LLM 注意力权重
├── 失败重试            → 覆盖瞬时调用失败
└── G-T1 staleness guard → 检测层：当 relay 确实缺失时，不展示过期数据
```

**观察期的架构角色**：数据驱动的风险验证。如果 3 周期 relay 更新正常 → 证明概率压缩策略有效，MAJOR 闭环。如果失败 → 带着真实数据评估是否需要架构升级。

**升级条件的架构合理性**：

```
升级条件: 连续 >3 周期无 relay 更新 → MAJOR→BLOCKER
```

- "连续 >3 周期"（非"任意 1 周期"）：避免单次 LLM 随机波动触发误报。3 周期的窗口足以区分"偶发遗忘"和"系统性失效"。
- 架构层面隐含假设：如果 relay 连续 3 周期不更新，说明 prompt-level fix 的概率压缩不够，需要更激进的架构手段（如非 LLM 预/后置钩子）。

### 2.2 架构隐患标注：观察期缺少自动化监控

**这是本次评审发现的唯一架构层面 gap。** 产品裁定描述了观察期（≥3 OC 周期）和升级条件（>3 周期无 relay 更新），但没有指定：

1. **谁来监控**？产品裁定未指定责任人。
2. **怎么监控**？当前架构没有 relay 更新频率的自动采集。
3. **怎么升级**？触发条件到 MAJOR→BLOCKER 升级之间没有自动化路径。

**建议**（不阻塞发版，验收期实施）：

在 watchdog collector 或独立 cron 中增加 relay staleness 监控：
```
每 tick 记录: relay phase 是否变化
连续 N tick 无变化 → 发送通知（不是 BLOCKER 升级，而是提前预警）
```
这在架构上是轻量的：collector 已有 `read_relay_state()` 和 staleness guard，加一个计数器 + 阈值判断即可（约 5 行代码）。

**但这是增强建议，不是当前发布的阻塞条件。** 手动监控 3 周期在操作上是可行的（Frank 或 QA 主动检查 relay 更新），自动化可以在验收期内补齐。

### 2.3 5 MINOR → P5 — 架构层面确认

**P5 won't fix 在架构层面是正确的**：

- R-R1（并发写）→ 原子 rename 已解决，加锁反而引入复杂度（锁管理、死锁风险）
- R-R2（瞬态 rename）→ best-effort 是正确模式，引入重试或等锁会增加 collector 复杂度，收益接近零
- R-R4（relay 残留）→ 双层防护已足够（SOUL.md 清理 + staleness guard），再增加 cron 清理脚本是过度设计
- R-R5（PATH）→ 运维问题，不是架构问题
- R-R6（phase 枚举）→ 松耦合是正确的架构选择

**这些"缺陷"实际上是架构 tradeoff 的正确一面。修它们会破坏架构的简洁性。**

## 议题 3: 修复难易程度 — D1 prompt fix 还是全功能改造？

### 裁定：强烈同意产品裁定。D1 prompt-level fix 是架构最优路径。

### 3.1 架构层面的根本约束

方案 C 的核心设计决策是：**OC orchestrator 保留 LLM 决策能力**。这个决策意味着：

```
┌─────────────────────────────────────────┐
│  OC orchestrator (LLM agent)            │
│  ┌─────────────────────────────────┐    │
│  │ 每次 tick:                       │    │
│  │  1. LLM 读取 kanban 状态         │    │
│  │  2. LLM 决策：派发/等待/完成     │    │
│  │  3. LLM 执行决策                 │    │
│  └─────────────────────────────────┘    │
│  所有步骤都经过 LLM                      │
└─────────────────────────────────────────┘
```

在这个架构下，**调用 relay_update.py 的可靠性受限于 LLM 遵循指令的可靠性**——与 enforcement 机制无关。

### 3.2 D1 fix vs 全功能改造：共享同一个概率底限

```
方案           │  enforcement 机制        │  可靠性上限
───────────────┼──────────────────────────┼─────────────────────
D1 prompt fix  │  prompt 规则（阶段 -1/0）│  LLM 遵循指令的概率
全功能改造     │  代码级 pre/post 钩子     │  LLM 调用钩子的概率
```

**关键洞察**：全功能改造的"代码级钩子"仍然需要 LLM agent 来触发。除非钩子脱离 LLM agent 独立运行（例如，在 OC cron 的 shell wrapper 层做 pre-hook），否则它和 prompt fix 共享同一个概率底限——LLM 是否执行这个步骤。

而脱离 LLM agent 的独立钩子直接推翻方案 C 的核心设计（保留 LLM 决策能力），等价于废掉方案 C。

**三种可能的架构路径对比**：

| 路径 | 机制 | 能否消除风险 | 架构代价 |
|------|------|:---:|------|
| **A: D1 prompt fix**（当前） | SOUL.md 强制前置规则 | 不能（概率压缩到极低） | 0 代码改动，已完成 |
| **B: 代码级钩子（LLM 触发）** | LLM agent 调用 pre/post hook | 不能（与 A 同底限） | 100-200 行代码 + 0.5-1 人天 |
| **C: 独立钩子（shell wrapper）** | cron wrapper 层强制调用 relay | **能**（绕过 LLM） | 推翻方案 C，OC 不再有 LLM 灵活性 |

路径 C 是唯一能彻底消除此风险的路径，但它的架构代价（推翻方案 C）远超收益（消除一个已大幅压缩的概率性风险）。

**结论：路径 A 是在不推翻方案 C 前提下的最优解。**

### 3.3 ROI 分析 — 架构视角

| 维度 | D1 fix | 全功能改造 | 差值 |
|------|--------|-----------|------|
| 改动量 | 0 代码（仅 SOUL.md） | ~100-200 行 Python | — |
| 测试成本 | 已完成（162 PASS） | 全套新测试 | — |
| 风险消除 | -99% 概率（估算） | -99.5% 概率（估算） | **+0.5%** |
| 边际收益 | — | — | **接近零** |

当两条路径共享同一个不可突破的底限时，额外投入产生的边际收益趋于零。在架构层面，这属于**超额投资陷阱**。

### 3.4 验收期观察的架构定位

观察期不是"推迟决策"，而是"在正确的时间做正确的决策"：

- **现在**：用最低成本（prompt fix）将风险压到极低 → 发布
- **3 周期后**：
  - 如果 relay 正常 → 证明概率压缩有效，MAJOR 闭环，投入 0
  - 如果 relay 异常 → 带着真实失败数据评估是否需要路径 C（shell wrapper），此时投入有据可依

这是架构层面的**渐进式风险管控**模式：先低成本降风险，再数据驱动定是否需要架构升级。
