## 1. 记忆中间层的实现形态：独立 repo「库 + CLI + skill」三层，无独立服务（问题 1）

三选项裁决：**不是独立服务，不是纯 skill，是「独立 git repo + Python 库 + CLI + 策展 skill」**。

| 选项 | 否决/采纳理由 |
|------|--------------|
| 独立服务（守护进程/HTTP） | **否决**。13 个 profile 同机运行，守护进程 = 新增可用性依赖（挂了记忆写不进去）+ 端口/生命周期管理。Karpathy 模式与 MemPalace 的核心卖点都是 local-first 文件 + 确定性检索，服务化把简单事做复杂。DevPPL 已有 cron/autopilot 常驻教训（DPL-013 在推动去常驻化），不应反方向引入新常驻 |
| 纯 skill + 手工文件操作 | **否决**。llm-wiki skill 现状就是纯 skill——500 行操作手册，所有解析/索引/lint 靠 agent 每次现做。OBS-01（LLM 忘记调 relay_update.py）已证明纯约定必失忆。确定性逻辑（解析、索引、漂移检测）必须进代码，LLM 只做语义策展 |
| **库 + CLI + skill（采纳）** | 确定性引擎（Python 包）被 CLI 封装为单一入口 `mem`，skill 只写"何时调、怎么策展"，agent 的每一步都有可校验的命令背书 |

**部署**：`/workspace/mem-core` 独立 git repo（与 devPPL/InfoManager 同级），理由与 R1 架构师论证 WIKI_PATH 独立 repo 一致：提交节奏不同（代码按 feature、wiki 按事件高频），混仓毁 git log；单一写入者靠 repo 权限强制。备份接入 manifest.yaml（BKP-003 模式，同 hermes_backup_push.sh 链路）。

**分层**：
```
/workspace/mem-core/
├── memcore/                # Python 库（确定性引擎）
│   ├── schema.py           # SCHEMA.md 的机器可读镜像（frontmatter 字段、链接解析规则）
│   ├── parse.py            # frontmatter + wikilink + 表格解析（容错）
│   ├── indexer.py          # SQLite 图索引 + trigram FTS5 + bigram 回退表
│   ├── blast.py            # 增量更新候选集计算（反向索引，零 LLM）
│   ├── drift.py            # 漂移检测（时间戳/状态/断链）
│   ├── context.py          # 会话上下文摘要（boot_context v2 的引擎）
│   └── lint.py             # 四不变式校验
├── bin/mem                 # CLI 入口：add / update / query / lint / drift / context / status
├── wiki/                   # 记忆正文（SCHEMA.md + index.md + log.md + actions/ + entities/ + raw/）
└── SKILL.md                # mem-worker skill 正文（策展协议，随 repo 走）
```

**关键点：wiki 正文与代码同 repo**。R1 方案 wiki 在 `/workspace/devPPL-wiki`、代码在 devPPL/scripts/gai/——两个 repo 两套备份两套同步。R3 合并为一个 repo：知识正文是引擎的"数据"，与引擎同版本、同备份、同测试夹具。SCHEMA 改动与解析器改动必须同步提交，lint 才能验证。这直接消掉 R1 方案里"wiki 的 SCHEMA 与 gai.py 解析规则分家"的隐患。

## 2. wiki-llm 工程化：从"agent 手动整理"到"确定性引擎 + LLM 策展"（问题 2）

### 2.1 skill 升级策略：借模式、不复用（R1 立场延续，加多副本同步）

通用 llm-wiki skill（13 份）保持研究型 wiki 用途不动；新建 **mem-worker skill**（随 mem-core repo 走）：
- 继承：frontmatter / [[wikilinks]] / index.md+log.md 导航 / 增量更新思想 / 每页 ≥2 出链；
- 定制：节点类型砍到 actions/ + entities/ + raw/（砍 comparisons/queries，决策档案用不上）；SCHEMA 写明「wiki 不存状态、不替代检索、不存事实偏好」三边界（R1 共识）；
- **多副本同步**：13 份 llm-wiki 副本本来就是各自 profile 的孤立拷贝，改不动也同步不动。mem-worker skill 只有一份（repo 内），各 profile 通过 `skills` 配置指向 repo 路径或由 boot_context 注入，避免再复制 N 份。

### 2.2 增量更新的工程实现：blast radius 确定性化

Karpathy 原版增量更新靠 LLM prompt（"列出受影响页面，先别改"）——每来一份新材料 LLM 都要在 context 里过一遍全 wiki，这正是 200 文件墙的成因。工程化方案：

```
mem update <source> --plan     # 确定性：把 source 按 term 切分 → 反向索引查候选页
                               #   （term → pages 映射在 indexer.py 构建时已算好，零 LLM）
                               #   输出：候选页清单 + 命中理由（哪些 term 命中）+ 新增页建议
mem update <source> --apply <pages...>   # LLM 只在候选集内读页、改写、bump updated
```

- 候选集计算 = 反向索引查表（O(term数)），不读全 wiki；
- LLM 的 context 成本从"全 wiki"降到"候选页 ≤10 个"；
- `--plan` 输出可人工/OC 裁定 blast radius（Karpathy 原版的人工确认环节保留）。

### 2.3 200 文件墙的目录索引方案：三层递减，不是一层

| 层 | 载体 | 作用 | 触发条件 |
|----|------|------|---------|
| L0 人读目录 | index.md + 分区子索引 | 一眼定位 | 每目录 >50 页拆子索引（llm-wiki 原规则保留） |
| L1 图索引 | mem_meta.db（SQLite） | pages/links/events 三表，出链入链、孤页、blast radius 全可查 | 构建即建，不设触发 |
| L2 全文检索 | trigram FTS5 + bigram 回退表 | CJK 子串检索兜底 | 构建即建 |

工程要点：mem_meta.db 是**派生数据**（由 wiki 文件确定性生成），不是第二真源。`mem index --rebuild` 幂等重建，`mem lint` 校验 db 与文件一致——这条不变式保证"文件是真源、db 只是加速缓存"，杜绝双写漂移（R1 GAI 双份拷贝的教训直接复用）。

## 3. 记忆宫殿增强：SQLite 图/时间索引现在做，ChromaDB 与 embeddings V3 再说，MCP 暂缓（问题 3）

MemPalace 三件套逐个裁决：

| 组件 | 裁决 | 理由 |
|------|------|------|
| **SQLite 时间实体关系图** | **MVP 采纳** | 正是 mem_meta.db 的角色：pages/links/events 三表 + `created/updated/source_task` 字段 = 可查询"某时点的知识状态"；drift 检测、blast radius、断链 lint 全建立在它上面。不是 Neo4j 式图数据库，SQLite 三表足够（决策档案的图规模 ≤10^3 节点） |
| **空间层次（Wing/Room/Shelf）** | **MVP 采纳（廉价）** | MEM-002 的实现 = SCHEMA.md 加 `location:` 枚举字段 + frontmatter 校验，1h 内。不引入额外导航设施——frontmatter 字段 + index 分区即空间层次 |
| **ChromaDB / embeddings** | **V3 可选，默认不做** | ① 本域语料是决策+机制说明，ID 化和结构化成度高，关键词/trigram 检索覆盖绝大多数查询；② MEM-005 已裁定 bge-small-en 中文噪声——若真上向量必须换 bge-m3-zh 类中文模型，是新增模型下载 + 推理依赖；③ 向量文件是第二写路径，与 git 文件的同步成本高于收益。若 V3 上，倾向 sqlite-vec（保持单一 SQLite 存储）而非 ChromaDB 独立存储 |
| **MCP 接口** | **暂缓** | 本环境 agent 与中间层的集成面是 CLI + skill + boot_context 注入，没有 MCP host 需求。等 Hermes 生态出现 MCP 消费方再包一层 adapter（预留 `mem mcp-serve` 占位，V3 3h） |

**本地确定性 vs LLM 策展的分工线**（写进 mem-core SCHEMA.md，违反即 lint 失败）：

| 归确定性引擎（代码，零 LLM） | 归 LLM 策展（agent） |
|------------------------------|---------------------|
| 解析 frontmatter/wikilink/表格 | 详情页四段正文撰写/更新 |
| 索引构建、反向索引、blast 候选 | 候选集内裁定"哪几页真要改" |
| 漂移检测（时间戳/状态/断链） | 矛盾识别与裁决（打 `contradictions:` 标记） |
| CJK 检索（trigram+bigram） | 新决策的语义归纳（为什么/怎么算完） |
| 状态镜像（kanban→wiki status） | — |

判定原则：**输出可机械校验的进代码，输出需要理解的进 LLM**。这条线是 R1 gai.py/gai-writer 分界的推广，也是整个中间层"零 LLM 也能跑、有 LLM 更聪明"的架构基础。

## 4. 跨会话接入：boot_context v2 读 wiki 摘要，写路径事件驱动 + 周 cron 兜底（问题 4）

### 4.1 读路径：boot_context.py 增强，不是替代

现 boot_context.py 每 5min 写 .hermes.md 动态段，读四源（pipeline_state/kanban/sessions/memory）。v2 增加**第五源 = mem-core context 引擎**：

```
mem context --scope project        # OC 会话：最近 24h 更新页 + 活跃任务关联决策页 + P1 未决页，≤800 字
mem context --scope task --id t_x  # worker 会话：该任务的决策页 + 关联实体页摘要，≤400 字
```

工程约束（R2 分步4 已承诺，延续）：
- **try-except 静默降级**：mem-core 缺失/脚本失败 → 跳过该源，5min 注入不得被 wiki 阻塞；
- 字符预算：boot_context 现有 2000 字符上限，wiki 段只占 ≤800，优先级低于 pipeline 活跃任务段；
- 不替代 session_search：wiki 摘要给"现在该知道什么"，session_search 给"过去发生过什么"，两个检索面不合并。

### 4.2 写路径：事件驱动为主（三层），轮询只做兜底

R1 裁决沿用并推广到整个中间层（不再只针对 GAI）：

| 层 | 触发 | 执行 | 强制力 |
|----|------|------|--------|
| 主路径 | **close.sh S3 替换**：`sed` → `mem done <ID>`（已有强制步骤，非新约定） | mem_cli | 强制（close 闭环验证入口） |
| 次路径 | kanban-worker / mem-worker skill 协议：创建任务/新决策时 `mem add` | mem_cli | 行为约定（接受失忆风险） |
| 兜底 | **周 cron `mem drift`**（只读，唯一 cron） | mem_cli | 滞后 ≤1 周可探测 |

为什么三层不能砍：OBS-01 是"LLM 忘记调 relay_update.py"的活案例，纯约定必失忆；事件驱动为主 + 周期对账兜底是唯一能在"零引擎改动"下闭合的架构。DPL-013（引擎事件钩子）落地后主路径整体迁移，约定层退役——V3 事项。

## 5. 与现有系统集成：kanban 事件源 → mem_cli → wiki；GAI 降级为应用层（问题 5）

### 5.1 kanban.db 事件源 → wiki 的管线

数据流单向（R1 共识，不变）：`kanban 事件 → mem_cli → wiki 详情页`，反向不成立。

| 事件 | 动作 | 挂点 |
|------|------|------|
| 任务创建 | `mem add task t_x` → 建决策页骨架（frontmatter 机械预填 + 参考材料自动收集） | kanban-worker skill 协议 |
| 任务完成/归档 | `mem done t_x` → 补结果节 + status=done + bump updated | **close.sh S3**（替换 sed） |
| 状态变更（阻塞/降级/P5） | `mem demote t_x --reason "..."` | kanban_block / comment 后 |
| 周对账 | `mem drift` 只读 diff（kanban vs wiki vs GAI 三方） | 周 cron |

### 5.2 GAI 作为应用的接入：从"被编辑的真源"降为"应用视图"

**这是 Frank 指示 2 对工程最大的简化，也是我 R3 最重要的反共识**：R1 我把 gai.py 表感知解析器估成 3h 最大难点（4 种表头 9 张表 + L47 脏单元格容错）——因为当时 GAI 是"必须解析后才能程序化写入"的真源。Frank 定性"GAI 待办条目没细节只是附属品/MVP"之后，**GAI 不再需要被程序写入语义细节**：

- GAI 表格保持 orchestrator 手工维护（OC/Frank 面向的 index 文档），细节全部住在 wiki 详情页；
- mem_cli 对 GAI 只做两件机械事：`mem gai-links`（给待办行补/校验 `[[ID]]` 命名双链）+ `mem drift` 里对 GAI 做断链/缺页检查（R1 gai_index.py --check 四不变式保留，但**不需要 gai.py 解析器了**）；
- close.sh S3 的 sed 换成 `mem done`（写 wiki 详情页 + 更新 GAI 状态列），对 GAI 的写仍是 sed 级替换——但这是从 wiki 状态镜像的展示更新，不是语义写入。

结果：**R1 的 gai.py 解析器 3h 预算整体消失**，GAI 适配器缩为 1.5h。中间层的核心预算全部投向 mem-core 本体，这才是 Frank 要的"完整开发中间层，不是做一个小功能"。

### 5.3 项目共享文件存储（GAI 待办的自然延展）

中间层本体 = 项目共享存储的骨架：`raw/` 收不可变源材料（roundtable 原始发言、QA 报告、审计输出），actions/ 收决策，entities/ 收机制/项目实体。跨项目知识（devPPL / InfoManager / Claude / 备份 等）各自 entity 页 + index 分区，天然形成项目共享知识面。这不需要单独设计"项目共享文件存储"功能——它就是中间层的 entities/ + raw/ 层。

## 8. 风险与反共识汇总

- **反共识 1（最重要）**：R1 的 gai.py 表感知解析器 3h 预算整体取消——Frank 定性"GAI 是附属品"后，GAI 从被解析的真源降级为应用视图，`mem gai-links` 1.5h 足矣。中间层预算全部投向引擎本体。这不是工时算术，是方案重心的转移。
- **反共识 2**：MEM-006 翻案——FTS5 trigram（零依赖）实测定能解决 CJK 检索，"不修"裁定基于错误前提，建议 P5 回炉并入中间层。
- **反共识 3**：wiki 正文与引擎同 repo（mem-core 一个 repo），推翻 R1 的"devPPL-wiki 独立 repo + devPPL/scripts/gai 代码"两仓方案——两个 repo 两套备份两套同步，SCHEMA 与解析器天然分家；同仓让 SCHEMA 改动与解析器改动必须同步提交、lint 可验证。
- **风险：mem_meta.db 是派生数据**——缓解：唯一真源是 wiki 文件，db 幂等重建 + lint 校验 db/文件一致（复用 GAI 双份拷贝教训）。
- **风险：worker 忘调 mem_cli**——缓解：主路径挂 close.sh S3（强制）+ 周 cron 兜底（滞后 ≤1 周可探测），与 R1 同构。
- **风险：回填质量参差**——缓解：只求四段非空 + ≥1 参考来源 + ≥2 出链（R1 共识验收），措辞靠 lint 迭代，不追求一次性完美。

## 9. 一句话结论

中间层 = 一个 repo（mem-core：引擎 + wiki 正文 + 策展 skill）+ 一条命令（mem CLI）+ 两个挂点（boot_context v2 读、close.sh S3 写）——确定性引擎扛检索/索引/漂移，LLM 只做策展，GAI 降级为第一个应用；MVP 9.5h 立起来，V2 10h 变厚，MEM-006 用 trigram 翻案、MEM-002/004 吸收，共 19.5h 把记忆从"玄学"变成可 lint、可漂移检测、可 30 秒追溯的工程系统。
