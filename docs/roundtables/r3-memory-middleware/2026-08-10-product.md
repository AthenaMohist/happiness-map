## 0. 先认账：R1/R2 把应用当成了系统

Frank 说"方向抓错了重点"，我认。

R1/R2 三方的方案本质是「GAI 自动更新 + 决策档案」——围绕 GAI 这张表建了一个 wiki 外壳。它回答了"GAI 待办怎么保鲜"，但没有回答"Hermes 的记忆为什么碎、为什么断、为什么不复利"。GAI 只是记忆的消费者之一，我们却把它当成了记忆系统本身。

R3 重新定性：

- **目标是系统**：Hermes 记忆中间层——以 wiki-llm 为核心，完整开发一个能沉淀、组织、检索、追溯 agent 长期记忆的中间层。要完整开发，不是做一个小功能。
- **GAI 是应用**：中间层建成后，GAI 待办详情、跨会话续接、项目共享文件存储都是顺带解决的场景。

下文按系统优先重排，不再以 GAI 为中心。

## 1. 核心痛点：中间层到底要解决什么

### 1.1 五个痛点（按 Frank 可感知程度排序）

| # | 痛点 | 现状证据 | 中间层解法 |
|---|------|---------|-----------|
| P1 | **纠正遗忘**：教过的又忘 | 梦境报告投递被纠正 3 次仍复发（Roundtable-B 量化：Frank 月浪费 7-17h） | 纠正事件自动落 wiki 页，跨会话可检索 → 二次纠正率归零 |
| P2 | **决策不可追溯**：不知道当初为什么这么定 | 32 行 GAI 待办只有标题无背景/验收；kanban 只有状态机，没有"为什么" | 决策页四段式（背景/问题/验收/参考），30s 追溯 |
| P3 | **记忆碎片化**：5 个存储互不相通 | memory（事实）/ mem0（事实）/ session_search（情节）/ kanban.db（状态）/ GAI（待办）各自为政，无结构、无互链、无复利 | wiki-llm 编译层：把各源知识编译成互链页面，知识只编译一次、持续保鲜 |
| P4 | **会话上下文断点**：换 session 就归零 | 100M token 上限被动切会话，OC 每次"失忆"，Frank 被迫重复解释 | 启动读取协议：新会话自动带出相关 wiki 页（最近纠正/活跃决策/当前任务） |
| P5 | **待办无细节**（副产品，Frank 点名） | GAI 32 行只有一行行动描述，无验收无背景 | 双链：GAI 行 → 详情页。这是中间层的第一个应用，不是目标 |

### 1.2 理想终态：Frank 的使用体验（五个场景）

1. **启动续接**：新会话第一轮，OC 主动说——"我们在做 X，上次你纠正过 Y（原因：Z），当前 W 在等。继续还是新话题？" Frank 不用教。
2. **决策追溯**：Frank 问"DPL-009 为什么这么做？" OC 30 秒内给出四段页：背景、要解决的问题、验收标准、参考材料——不用翻聊天记录。
3. **纠正复利**：同一错误只纠正一次，之后所有会话自动规避。"梦境报告投递"永远不再犯。
4. **知识积累**：Frank 说"看看我们之前调研过的 embedding 方案" → OC 直接给出比较页（含结论和取舍），不是"我搜一下历史"。
5. **状态与原因分离**：看板回答"现在什么状态"（L0 机器写），wiki 回答"为什么是这个状态"（L3 策展写）。两个问题各有真源，互不污染。

### 1.3 北极星指标（中间层是否成功的唯一判据）

**Frank 重复教的次数是否归零。**

- 辅助指标：决策追溯时长 ≤30s；新会话首轮主动带出正确上下文；同一纠正跨会话复发次数 = 0。
- **反指标（不是成功标准）**：wiki 页数、GAI 同步率、双链覆盖率。页面多是手段，"不重复教"才是目的。所有验收断言都往北极星靠，不往页数靠。

## 2. 中间层定位：补充层（L3），不是替代、不是抽象层

### 2.1 一句话定位

**中间层 = Hermes 记忆的「知识编译层」**：消费 L1 情节（session_search 的原始对话）和 L2 事实（memory/mem0 的原子记忆），编译成互链的、结构化的、可追溯的知识页面。

### 2.2 与原生记忆的关系（四条产品规则）

| 规则 | 内容 | 理由 |
|------|------|------|
| R1 **不替代注入** | memory/mem0/learn/journey 的每轮注入机制保持原样 | wiki 页太大不能注入。注入型记忆解决"当前该记住什么"，检索型知识解决"为什么/怎么做"。两层分工，不是竞争 |
| R2 **接管深检索** | 需要"为什么/背景/取舍"时去 wiki，不靠 FTS5 全文碰运气 | FTS5 无 CJK 分词（MEM-006）已实测全文检索对中文不可靠；结构导航（目录/双链/层次）才是可靠路径 |
| R3 **写入靠事件，不靠自觉** | 纠正/决策/完成任务等事件自动触发写入，接进现有强制流程 | 历史教训：OBS-01 证明"LLM 记得手动调用"是失败模式；知识不自动流入的 wiki 是死 wiki。这条决定中间层生死 |
| R4 **单一写入者** | wiki 只允许一个机制写，Frank 只读 | 记忆不可再生。写入者竞争 = 漂移与分叉（GAI 双份拷贝分叉 33 天是前车之鉴） |

### 2.3 为什么不是"抽象层"

"抽象层"会暗示统一封装 mem0/session_search/memory 成一套 API。产品判断：**不统一**。三层检索语义不同、消费场景不同：

- memory/mem0 = 注入型（每轮全量注入，原子事实）
- session_search = 情节型（按需全文，原始历史）
- wiki = 结构型（按需导航，编译知识）

强行抽象成一层 = 让简单问题背上复杂度，且改造 mem0/session_search 的成本远超收益。中间层只做它们都做不到的事：长期、结构化、可追溯。**它是新增的第三层，不是包住前两层的壳。**

### 2.4 一个产品补充：跨记忆会话与项目共享文件存储

Frank 提到这两项会"自然而然地产生解决办法"，我确认这个判断并给出机制：

- **跨记忆会话** = 中间层的读取平面。wiki 存编译知识后，新会话按主题拉取相关页，跨会话问题在读取侧解决，不需要再造一套"会话记忆同步"。
- **项目共享文件存储** = wiki 仓库本身。独立 git repo + 接入备份链（BKP-003 模式），天然多机同步、历史可查。多项目 = 多 WIKI_PATH（项目级 wiki），不是一张大 wiki。

## 3. 优先级排序：wiki 核心 > 写入通道 > 读取协议 > 记忆宫殿 > GAI

### 3.1 排序与理由

| 优先级 | 组件 | 产品理由 |
|:---:|------|---------|
| **P0-1** | wiki-llm 核心（存储骨架 + SCHEMA + 增量更新 + 双链约定） | Frank 钦定绝对核心。没有存储，一切免谈。Karpathy 模式的灵魂是"知识只编译一次、持续保鲜"（compiler, not search engine）——增量更新约定必须在 SCHEMA 第一天内置，这是与"建个文件堆"的本质区别 |
| **P0-2** | 自动写入通道（纠正/决策/完成任务 → 页面） | **中间层的命门**。R1/R2 吵的"自动更新 vs wiki 本体"其实是同一件事的两面：没有自动写入的 wiki 是死的。写入通道与存储骨架必须同批交付，否则骨架是空壳 |
| **P1-1** | 启动读取协议（会话启动拉取相关页） | 直接命中痛点 P1/P4（纠正遗忘 + 上下文断点）。铁律 6 的升级版——从"查 session_search"升级为"查 wiki 相关页" |
| **P1-2** | 记忆宫殿增强（空间层次导航） | 不是可选配件，是 wiki 规模化的必经之路。200 文件墙是 Karpathy 模式的已知墙；Wing/Room/Shelf 层次 = wiki 的目录分类法。在内容量级到达之前建好导航，防止 wiki 变成第二个不可检索的垃圾场 |
| **P2** | GAI MVP（P1 七行双链试点） | Frank 点名"附带品"。价值是**验证闭环**（从 GAI 行点进详情页、追溯可用），不是中间层的目标。不做 gai.py 全家桶 |

### 3.2 为什么记忆宫殿排在 GAI 前面

- GAI MVP 解决的是"一个应用的表单细节"（32 行待办回填），价值密度低，且它只是中间层的消费者。
- 记忆宫殿解决的是"wiki 增长后的可导航性"，是中间层自己的规模问题。先解决系统自身的扩展性，再喂应用。
- **但记忆宫殿 ≠ 立刻做重组件**：第一批只做分类法设计（SCHEMA 里定层次语义 + 目录级索引策略），ChromaDB/向量组件等 wiki 内容 >50 页或出现"找不到页"再投入。防墙的机制要早设计，墙的建材可以晚买。

## 4. mem 相关 7 条目逐一评估

判定标准：是否属于"记忆系统本身"——属于则并入中间层；属于 mem0/搜索引擎等外围则独立或废弃。

| ID | 条目 | 原定 | 产品判定 | 理由 |
|----|------|:---:|---------|------|
| MEM-001 | /learn + /journey 启用 | P1, 1d | **并入中间层**（作为 L2 写入源） | /learn 是 Frank 显式教的入口 = 纠正/偏好事件最直接的捕获点，P1 价值属实。但**并入而非独立启用**：learn 内容必须同时映射到 wiki 概念页，否则变成第 6 个孤岛。启用动作可与写入通道同批做 |
| MEM-002 | Session 层次标签 Wing/Room/Shelf | P2, 1h | **并入中间层**（语义迁移为知识页分类法） | 这正是记忆宫殿的空间层次思想（任务书已点名）。但产品要求**语义迁移**：标签对象从"session 流"改为"wiki 知识页"。session 是流（episodic），不适合打空间标签；知识页是积木（structured），才需要 Wing/Room/Shelf 导航。原 1h 卡片不单独做，SCHEMA 设计时一起定分类法，避免标签体系做两遍 |
| MEM-003 | 完整 LLM pipeline 未测试 | P3 | **独立**（维持 P3，不并入） | mem0 平台侧质量债（QA 已判 SUGGESTION），与中间层架构零耦合。注意：中间层的语义写入有自己的 LLM 路径，那套必须可测试（golden file），是**新的**测试需求，不是 MEM-003，不能拿这张卡的 P3 掩盖中间层的测试义务 |
| MEM-004 | LLM-Wiki [[wikilinks]] | P3, 2h | **并入中间层，升格 P0（绝对核心）** | Frank 钦定。原 2h 估的只是双链语法；现在 scope 扩为"wiki 核心骨架 + 增量更新 + 双链约定"，就是 P0-1 本体。**从 P3 待办升格为 P0 主干**，这是本次评估最重要的变化 |
| MEM-005 | bge-small-en 中文噪声 | P5 不修 | **废弃**（选型规避，零独立工时） | 中间层主路径不依赖 embedding（结构导航 + 精确匹配够用）。将来若加语义检索（记忆宫殿），直接选 multilingual embedder，等于在新组件里规避旧缺陷。不为 mem0 单独修，卡面关闭 |
| MEM-006 | FTS5 无 CJK 分词器 | P5 不修 | **维持不修**（中间层不背债） | FTS5 是 L1 session_search 的短板，属于"搜索引擎迁移"另一个议题。中间层检索走结构导航，不依赖 FTS5。别让中间层背负 L1 的历史债；同时把"中间层不依赖 FTS5"写进 SCHEMA，防止后人误以为 wiki 有全文搜索 |
| DPL-011 | 跨会话记忆（铁律6 + 纠正自动写 + 跨会话摘要） | 已归档 | **并入中间层，升格为读/写/摘要三协议** | 它就是中间层的种子：铁律6 → 启动读取协议；P1 纠正自动写 → 写入协议（E1 纠正事件）；P2 跨会话摘要 → wiki log.md + 会话摘要页。已归档卡不复活，但其验收目标"纠正不再重复"直接成为中间层北极星指标 |

**汇总：并入 4 项（MEM-001 / MEM-002 / MEM-004 / DPL-011），独立 1 项（MEM-003），废弃/维持 2 项（MEM-005 / MEM-006）。**

一句话版：**四条并入的条目恰好拼出中间层本身**（MEM-004=存储、MEM-001=写入源、MEM-002=导航、DPL-011=协议）；两条不修的是外围层历史债；一条独立的是平台侧质量债。7 条里没有一条需要独立于中间层单飞。

## 5. MVP 边界：最小纠正闭环（写 → 存 → 读）

### 5.1 MVP = 把「纠正闭环」跑通

中间层的价值链：Frank 纠正/决策 → 写入 wiki → 跨会话检索 → Frank 不再重复教。
MVP 只做这一条闭环，其余全部后置。

### 5.2 MVP 做什么（三平面各取最小件）

| 平面 | MVP 内容 | 对应痛点 |
|------|---------|---------|
| 存 | wiki repo 初始化 + SCHEMA（增量更新约定、单一写入者、四段页模板、目录级索引策略预留）+ entities 首批页 | P2 决策追溯 |
| 写 | 写入通道最小集：纠正事件 + 决策事件 + 完成任务 → 页面（接进已有强制流程，如 close.sh S3；不新增"记得调用"类约定） | P1 纠正遗忘 |
| 读 | 启动读取：会话开始自动带出最近纠正/活跃决策（铁律 6 升级版，可先手写协议再脚本化） | P4 上下文断点 |
| 验证 | GAI P1 七行双链试点（每行 [[ID]] → 详情页），证明"从表点进页、30s 追溯"这条链路真能用 | P5 待办无细节 |

### 5.3 MVP 明确不做（防止范围蔓延）

- ❌ 记忆宫殿完整实现（ChromaDB/层次导航组件）——只定分类法，组件等 wiki >50 页再做
- ❌ gai.py 全家桶（add/done/demote/list + 表感知解析器 + 周漂移对账）——GAI 只是验证场景，不是中间层
- ❌ GAI 全量回填 32 行——纯体力活，中间层稳定后再说
- ❌ mem0 任何改动（含 MEM-003）——平台侧独立债
- ❌ 搜索引擎迁移（FTS5 CJK）——L1 历史债，不并入

### 5.4 一周内 Frank 可见价值（验收）

1. Frank 纠正一次（如：梦境报告投递方式）→ 该纠正自动落 wiki 页（四段非空）。
2. 新会话第一轮，OC 主动说出最近纠正与活跃决策（试点 2 个已知纠正场景）。
3. Frank 问"某 GAI 待办为什么存在" → 30s 内从表点进四段详情页。
4. 下周任意会话，同一错误不复发（北极星指标首个观测点）。

---

## 6. 一句话结论

R1/R2 把应用当成了系统，R3 回归系统本身：**以 wiki-llm 为核心建 Hermes 记忆中间层——事件驱动写入、结构导航读取、增量编译保鲜；GAI 只是它的第一个验证场景。MVP 只跑通「纠正闭环」一条价值链，北极星是 Frank 重复教的次数归零。**
