## 一、Frank 的裁定回顾

1. **补充需求（核心）**：autopilot = 可接受指令的导航器——可定制流程、能接收指令、能叫停。目的：避免啥事都靠 OC 自己（OC 总是试图打破流程）
2. **F1**：同意 Gap 4 合并进通知 cron，但**每个 tick 输出 heartbeat 到飞书**
3. **F2**：能接收指令规划流程，实现路线不限
4. **F3**：Gap 3 workspace_kind 合规扫描 = P1

## 二、R2 三方收敛结果

### 1. 导航器形态（三方一致）✅

**指令卡通道（kanban `[CMD]` 卡）+ 现有 autopilot 引擎 + 流程映射**

- OC 的输入从"操作"变成"意图"——发一条 `[CMD] roundtable B 议题: xxx`，autopilot 按流程定义自动建卡、派发、汇总
- **v1 五类指令**：roundtable 发起 / create 建卡 / pause / resume / abort（自定义流程 v2 推后）
- **指令卡契约**：单次消费幂等 / assignee=autopilot / 滞留 3 tick 告警 / 失败有回执 / 叫停=状态标记不 kill

### 2. ⚠️ 重大发现：discover 误注册 bug（architect + engineer 双实锤）

**`discover.py` 的 PIPELINE_ASSIGNEES 已含 "autopilot"，但 SUB_TASK_TITLE_PREFIXES 没有 "[CMD]"** → 一张 `[CMD] roundtable B ...` 卡会被当作 dev 任务注册、assigned_agent=game-engine **派给开发 worker**！

**修复方案（4 道闸）**：
| # | 闸 | 性质 |
|---|-----|------|
| 1 | cmd_channel.sh 先于 discover 消费并归档 [CMD] 卡 | architect，顺序敏感 |
| 2 | discover.py SUB_TASK_TITLE_PREFIXES 加 `("[CMD] ",)` | architect，1 行 |
| 3 | **PIPELINE_ASSIGNEES 移除 "autopilot"** | engineer 补，**根治**（现库 0 存量，影响面 0） |
| 4 | stuck_check + dedup_check + workspace_check 防御性排除 | architect + engineer，各 1-3 行 |

### 2.5 engineer 补充（#849，重复卡 t_be35aebf 已归档，存档保留）

- **dedup_check.sh 归档路径是最高危遗漏**：它会主动归档重复卡——`[CMD]` 卡若被误判为重复，命令会被**静默吞掉**。必须跳过 `[CMD]` 卡（比 discover 误注册更危险）
- **cmd_channel.sh 挂载点陷阱**：必须挂在 autopilot.sh **主 flock 之前**——挂在锁内 = 每 tick flock 冲突 → 命令永远不被消费
- **notify snapshot diff key 坑**：`upsert_step` 用 INSERT OR REPLACE → snapshot diff 的 key 绝不能用 rowid，必须 (task_id, step_name)
- **建卡契约补充**：`initial_status='blocked'` 防御未来注册 autopilot profile 的竞态（hermes profile list 当前无 autopilot，[CMD] 卡天然不被 dispatcher 派发）
- **工期修正**：~1.5 人日（通知 cron 0.5d + cmd_channel 原子集 0.5d + task_control 0.25d + workspace_check 0.25d），与 #848 的 15.5h 口径一致（1 人日≈10h）

### 3. 叫停机制（三方一致）✅

**`task_control` 表（pipeline_state.db v3 migration）+ advance_pipeline 入口检查**
- pause：只写控制位，步骤状态不动 → resume 清控制位即从断点继续
- abort：写控制位 + 全部活跃步骤置 cancelled + 归档卡 → get_active_tasks 自动剔除，不再推进
- **不 kill 进程**：worker 自然结束或被 dispatcher 超时回收

### 4. heartbeat 设计（三方一致）✅

- **三条独立 emit 路径**：exception（实时）/ milestone（聚合 ≤1/tick）/ heartbeat（每 tick 1 条）
- 格式：`[AP 14:32] 活跃3 跑1 堵0 今完2 | t_abc dev done`（一行 ≤80 字）
- **去重语义二分**：heartbeat 本体不去重（Frank 要求每 tick）；变化附注 event_hash 冷却 30min
- 逃生阀：`heartbeat_enabled` + `silent_window`（22:00-08:00 不推 heartbeat，例外照推）
- engineer 修正：**飞书 token 必须缓存**（现有实现是两步 API 非 webhook，不缓存 = 720 次/天 token 请求必被限流）

### 5. notify_state.db schema 定稿（engineer 精简）

**三表 → 两表**（dedup_cooldown 并入 notify_events.last_sent_at）：
- `notify_events(event_hash UNIQUE 不含 detail, event_type, task_id, step, status, detail, first_seen_at, last_sent_at, push_count)`
- `pipeline_snapshot(task_id, step, status, updated_at, PK)` — diff 基准
- 7 天滑动窗口清理

### 6. 技术路线（三方一致）✅

**复用 kanban 卡通道胜出**——唯一不引入第二状态系统的路线。真实成本 = **指令平面排除集**（4 处，~1h 确定性工作）。

## 三、实施工期（engineer 估算）

| 模块 | 工期 |
|------|------|
| 通知 cron（Gap1+4+F1 heartbeat + token 缓存） | **6.5h** |

## 四、关键验收标准（建议写进任务卡）

1. **[CMD] 前缀保留 + 4 处排除集**随指令通道一起上线（不能拖后，上线瞬间就有人发第一条指令）
2. **硬验收**：手动造一张 `[CMD] roundtable B 测试` 卡，跑 1 tick，验证：(a) 1 tick 内消费并归档；(b) pipeline_state.db 零 dev 步骤记录；(c) dedup/stuck/workspace_check 三脚本都不报它
3. **飞书 token 缓存**为通知 cron 验收第一条
