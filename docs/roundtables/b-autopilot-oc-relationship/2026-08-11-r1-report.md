# B 类 Roundtable 报告：OC/autopilot 关系重构方案

**日期**：2026-08-11
**类型**：B（头脑风暴）
**参与者**：product（许清楚）/ architect（高见远）/ engineer（寇豆码）
**议题**：Frank 裁定 OC 不再建卡、autopilot 自动走流程并汇报后，autopilot 还缺什么功能？

---

## 一、Frank 的新规则（议题背景）

> 理想状态是 autopilot 自动走流程并汇报，OC 作为监管，保证 ppl 流程健康。如果流程进行正常，OC 不应做任何多余的事。**OC 不再建卡**，但可以删卡或归档卡。OC 建卡应通过 autopilot 进行。

## 二、已确认的事实（实锤）

1. autopilot = 独立 cron（每 2 分钟），deliver=local，**不依赖 OC session**
2. OC 停了：autopilot ✅ 继续跑 / worker ✅ 继续被 dispatch / worker 完成通知 ✅ 到飞书 / **autopilot 主动汇报 ❌ 无法到飞书**
3. autopilot 已有 13 项能力（任务发现/状态推进/10步建卡/fanout/merge/close/roundtable/rollback/retry/block/dedup/stuck）
4. autopilot.sh 共 704 行，单脚本结构，已到可维护性临界点

## 三、5 个缺口 + 三方判断汇总

### Gap 1：autopilot 无飞书汇报通道 🔴 P0

| 角色 | 方案 | 判断 |
|------|------|------|
| product | **方案 C（独立通知 cron）**：例外驱动——error/block/rollback/gate/retry-exhausted/stuck 实时推；里程碑聚合推（每 tick ≤1 条）；例行状态不推 | P0，信任基石 |
| architect | 同意 C，补 4 个约束：①自建 `notify_state.db`（不污染 pipeline_state.db 单一写入者契约）；②信号源 = DB 状态迁移为主 + kanban comment `[AUTOPILOT:` 前缀为辅，**不用 log grep**；③feishu 配置外置 config/notify.json；④fail-open 独立进程 | P0 |
| engineer | 同意 C（~140 行），**但推荐在 pipeline_state.db 加 `pipeline_events` 表**而非独立 notify_state.db；飞书 webhook 就是一行 curl | P1 |

**分歧点**：architect 主张 notify_state.db 独立（遵守"只有 autopilot 写 pipeline_state.db"契约）；engineer 主张 pipeline_events 表加在 pipeline_state.db 里（autopilot 写，通知 cron 读）。**这个分歧需要 Frank 或 R2 裁定。**

### Gap 2：autopilot 不能接受"建卡"指令 🔴 P1（可能是伪需求）

| 角色 | 判断 |
|------|------|
| product | P1，技术已通（task discovery L76-102 自动注册手动卡），缺文档化 |
| architect | 验证属实——`hermes kanban create` → 2 分钟内 autopilot 自动发现接管 |
| engineer | **质疑伪需求**——discover_new_tasks 已覆盖 OC CLI 建卡路径，0 行代码改动 |

**结论**：Gap 2 大概率是**伪需求**。OC 用 `hermes kanban create` 建卡，autopilot 自动接管。真正缺的是 Gap 5（内容注入）。

### Gap 3：workspace_kind 合规扫描缺失 🟡 优先级争议

| 角色 | 判断 |
|------|------|
| product | P2 backlog（当前风险暴露面有限） |
| architect | 同意 P2，但若做则是 scripts/workspace_check.sh（同 dedup/stuck 模式，~1h） |
| engineer | **建议 P1**——main 分支直改是代码安全红线，比健康度报告更紧急（~60 行，复刻 dedup_check） |

**分歧点**：P2 vs P1。engineer 认为"禁 main 直改"是代码安全红线应该提前。

### Gap 4：管线健康度报告缺失 🟡 P1

| 角色 | 判断 |
|------|------|
| product | P1，OC 监管前置依赖（每 30 轮=1h 输出摘要） |
| architect | **应合并进 Gap 1 通知 cron**，不独立建 cron（避免两个 cron 重复读库+发飞书） |
| engineer | 依赖 Gap 1（通知通道），必须串行；报告推送到飞书才有人看 |

**结论**：三方一致认为 Gap 4 依赖 Gap 1，不独立实现。

### Gap 5：手动建卡无内容注入 🟢 P1（合并进 Gap 2）

三方一致：在 discover 注册循环后补 ~10 行 bash，注入标准 comment（claim 要求 + wiki 链接 + 超轮次提醒）。

## 四、核心分歧清单（需 Frank 裁定或 R2 辩论）

| # | 分歧 | product | architect | engineer |
|---|------|---------|-----------|----------|
| 1 | **notify_state.db vs pipeline_events 表** | 未表态 | 独立 notify_state.db（契约） | pipeline_state.db 加表（简单） |
| 2 | **Gap 3 优先级** | P2 backlog | P2（若做则同级脚本） | P1（代码安全红线） |
| 3 | **Gap 2 是否伪需求** | 认为存在 | 验证属实 | **认为伪需求** |

## 五、三方共识（无争议）

1. **Gap 1 方案 C（独立通知 cron）正确**——三方一致
2. **产品红线：不骚扰**——汇报第一优先级是"宁漏推里程碑，不可错推例行状态"
3. **autopilot.sh 704 行不许再膨胀**——所有新功能走独立脚本挂载模式（dedup/stuck 模式），不塞主循环
4. **通知 cron 读 pipeline_state.db（结构化），绝不读 autopilot.log（非结构化文本）**——三方一致
5. **Gap 4 依赖 Gap 1，不独立实现**——三方一致

## 六、engineer 额外发现

- **架构隐患**：discover.py 的 `register_discovered_task()` 硬编码 `assigned_agent="game-engine"` + `step_name="dev"`。手动建 assignee=game-qa 的卡会被错误注册为 dev 步骤。建议记入 backlog。
- **工程风险**：704 行单脚本已混合业务逻辑 + 基础设施；每个 action 分支内联大量 `python3 -c` 调用；无 source 控制拆分（只有 1 个 lib）。

## 七、建议

1. **分歧 1（状态库位置）**：建议 R2 让 architect + engineer 交叉辩论一次，或 Frank 直接裁定。engineer 的方案实现成本更低（~40 行 vs 独立库），但 architect 的方案更守契约。
2. **分歧 2（Gap 3 优先级）**：建议接受 engineer 意见提到 P1——"禁 main 直改"是昨天刚踩的坑，趁热打铁。
3. **分歧 3（Gap 2 伪需求）**：建议接受 engineer 判断——OC 建卡走 `hermes kanban create`，autopilot 自动接管，省掉一个不必要的功能开发。
