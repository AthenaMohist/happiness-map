## 1. 背景

### 1.1 原始任务

| 字段 | 值 |
|------|-----|
| P0 编号 | P0-05 |
| 原始 kanban 任务 | infomanager board `t_b66db2fa` |
| 标题 | Infomanager 管线加结构化日志（0.5h） |
| 性质 | 基础设施增强：可观测性 |
| 实现状态 | ⚠️ **实现任务尚未创建**（infomanager board 上缺失 P0-05 实现卡片；P0-01~P0-04/P0-06 均存在） |

### 1.2 问题陈述

Infomanager 管线当前缺乏结构化日志。排查管线问题（如 URL 消失、import 路径错误、审计覆盖率不足）时，运维和 QA 只能依靠猜测和间接证据，无法快速定位故障点。

具体影响：
- **P0-04（URL 消失根因）**：没有管线日志记录 URL 写入/读取的完整路径，无法追溯何时丢失
- **P0-01（$HOME → /root）**：审计发现 importer 路径错误，但无日志记录当时的解析值
- **P0-06（contract test + e2e）**：测试依赖 stdout 输出，非结构化、无法机器解析

### 1.3 可观测性维度（标准 §12）

本测试方案以标准 §12 为核心框架，覆盖两个层次：

| 层次 | 标准引用 | 内容 |
|------|---------|------|
| **P0（当前关注）** | §12.1 | 回归范围声明、Schema 变更影响面、可复现性门禁、跨团队 SLA、环境差异处理 |
| **P1（前瞻性设计）** | §12.2 #3 | 可观测性退化监控：BLOCKER/MAJOR 关闭时 QA 标注 `observability_gap: true/false`，积累 3 个月数据后评估各模块日志完备性 |

本方案的测试用例设计旨在让 P0-05 实现完成后，QA 能对每个 finding 标注准确的 `observability_gap` 状态。

## 2. 测试策略

### 2.1 两层测试结构

P0-05 目前处于「实现前」状态——实现任务尚未创建。因此测试方案分两层：

| 层 | 阶段 | 目标 | 执行时机 |
|----|------|------|---------|
| **L0：前置检查** | 实现前 | 确认实现任务的 6 项前置 QA 要求已满足 | 研发创建实现任务后、开始编码前 |
| **L1：功能验证** | 实现后 | 验证结构化日志的 6 个质量维度 | 实现完成、提交 code review 后 |

### 2.2 L0：6 项前置 QA 检查清单

在研发开始实现前，QA 必须确认以下 6 项已明确并在实现任务中记录。这 6 项来自 P0-01~13 伞形测试方案的初始建议：

| # | 检查项 | 判定标准 | 缺位风险 |
|---|--------|---------|---------|
| **C1** | JSON schema | 日志格式定义 JSON schema 文件，包含至少：`timestamp`、`level`、`pipeline_stage`、`message`、`trace_id` 字段 | 无 schema → 日志不可机器解析 → 无法自动化告警 |
| **C2** | 日志级别 | 明确定义 DEBUG/INFO/WARNING/ERROR 的使用边界。ERROR：管线不可恢复故障。WARNING：可恢复异常但需要关注。INFO：管线阶段转换。DEBUG：内部状态快照 | 级别混乱 → ERROR 泛滥导致告警疲劳，或关键错误被淹没 |
| **C3** | Trace ID | 单次管线执行从入口到出口使用同一 trace_id。跨阶段（ingest→process→store）可关联。多次管线执行间 trace_id 不重复 | 无 trace_id → 跨阶段故障无法串联 → 根因定位靠猜 |
| **C4** | 错误上下文 | ERROR 日志携带：异常类型、堆栈前 3 帧（或 trimmed）、失败的输入数据标识（如文件路径/消息 ID）、重试次数（如适用） | 错误无上下文 → 「管线某处失败了」→ 0 信息量 |
| **C5** | PII 不泄露 | 日志中不出现：API key、token、密码、手机号、邮箱（除非脱敏）、IP 地址（内部系统可保留） | PII 泄露 → 安全漏洞（§2，附录 B 补充：PII 泄露 → 最低 MAJOR） |
| **C6** | 日志量可控 | 通过配置控制日志级别（如 `LOG_LEVEL=INFO` 生产 / `DEBUG` 调试）。预估正常流量下的日志体积（MB/day），超过预期阈值有告警 | 日志量失控 → 磁盘耗尽 → 生产事故 |

**QA 判定**：6 项全部满足 → L1 允许开始。任一项缺失 → **BLOCKER**（前置条件不满足），需研发补充后再进入 L1。

> **判定依据**（标准 §1.2）：
> C1-C6 任一项缺失 → 用户可感知 ✓（日志质量直接影响故障响应时间） + 功能阻断 ✓（无法实现可观测性目标） + 无 workaround ✓（只有正确实现才有用）
> → **BLOCKER**（前置条件不满足，非代码 bug，属流程级阻断）

### 2.3 L1：6 个测试维度

L1 测试维度与 L0 前置检查一一对应，但 L1 是**运行时验证**——不仅要确认规范存在，还要确认实现符合规范：

| 维度 | L0（文档检查） | L1（运行时验证） | 测试用例对应 |
|------|:---:|---|:---:|
| JSON schema | C1：schema 文件存在 | 实际产出的日志行通过 JSON schema 验证 | TC-01 |
| 日志级别 | C2：级别定义 | 正常/异常场景下产出的日志级别符合定义 | TC-02 |
| Trace ID | C3：trace_id 定义 | 同一次管线执行为同一 trace_id；跨执行不重复 | TC-03 |
| 错误上下文 | C4：上下文定义 | ERROR 日志携带完整的异常类型 + 输入标识 + 堆栈 | TC-04 |
| PII 不泄露 | C5：规范 | 实际日志行中不包含敏感数据（正则扫描 + 人工抽查） | TC-05 |
| 日志量 | C6：预估 | 正常流量下日志体积在预期范围内；DEBUG 模式可切换 | TC-06 |

## 3. 测试用例

> **注意**：以下测试用例在 P0-05 实现完成前无法执行。用例规范供实现后 QA 直接使用，无需重新设计。

### TC-01：JSON Schema 符合性

```
Given: 管线至少完成一次完整的 ingest→process→store 全流程
When:  收集所有产出日志行
Then:  每行都是合法的 JSON（可被 json.loads() 解析）
       AND 每行包含以下必填字段：timestamp、level、pipeline_stage、message
       AND 可选字段 trace_id 存在且非空
       AND timestamp 为 ISO 8601 格式（含时区）
       AND level 在 ["DEBUG", "INFO", "WARNING", "ERROR"] 中
       AND pipeline_stage 在定义阶段名中（如 "ingest", "process", "store"）
```

### TC-02：日志级别正确性

```
Given: 管线按预期执行（正常输入 + 正常处理）
When:  收集 INFO+ 级别日志
Then:  不产生 ERROR 级别日志
       AND 每个阶段转换点有 INFO 日志（"stage=ingest completed", "stage=process started"）
       AND WARNING 仅在可恢复异常时产生（如重试成功）

Given: 管线遇到不可恢复错误（如磁盘满、网络超时耗尽重试）
When:  收集全部日志
Then:  至少产生 1 条 ERROR 日志
       AND ERROR 日志包含异常类型 + 失败原因描述
```

### TC-03：Trace ID 关联性

```
Given: 启动一次完整的管线执行（单条消息的 ingest→process→store）
When:  收集该次执行的所有日志行
Then:  所有日志行的 trace_id 字段相同（同一值）
       AND trace_id 为 UUID v4 或等价唯一标识格式

Given: 连续启动 3 次独立管线执行
When:  收集 3 次的日志行
Then:  3 次的 trace_id 互不相同
       AND trace_id 无碰撞（36 字符 UUID 格式）
```

### TC-04：错误上下文完整性

```
Given: 故意触发管线 ERROR（如：传入损坏的 JSON、目标存储路径不可写）
When:  收集产生的 ERROR 日志行
Then:  ERROR 日志包含：
       - 字段 "exception_type"（如 "ValueError", "PermissionError"）
       - 字段 "input_identifier"（失败的输入文件路径/消息 ID）
       - 字段 "stack_trace"（至少前 3 帧）或 "stack_trace_trimmed": true
       - 有重试逻辑时，字段 "retry_count" 记录已重试次数
```

### TC-05：PII 防泄露

```
Given: 管线处理包含敏感数据的输入（如含 API key 的配置文件、含手机号的消息）
When:  收集所有日志行
Then:  日志中不出现：
       - 正则匹配：sk-[a-zA-Z0-9]{20,}（OpenAI key 格式）
       - 正则匹配：m0-[a-zA-Z0-9]{32,}（mem0 key 格式）
       - 正则匹配：1[3-9]\d{9}（中国手机号格式）
       - 正则匹配：[\w\.-]+@[\w\.-]+\.\w+（邮箱格式，除非已脱敏为 xxx@xxx）
       - 包含 "password", "secret", "token", "api_key" 等关键词且后跟非空值
```

### TC-06：日志量可控

```
Given: 管线处理 100 条正常消息（模拟标准流量）
When:  设置 LOG_LEVEL=INFO
Then:  总日志体积 < 10 MB（粗略阈值，实际需根据管线复杂度调整）
       AND 无单条日志超过 10 KB（防止堆栈不截断导致单行膨胀）

Given: 管线处理 1 条消息
When:  设置 LOG_LEVEL=DEBUG
Then:  日志行数 > INFO 模式下的日志行数（DEBUG 输出更多内部状态）
       AND 切换回 LOG_LEVEL=INFO 后，日志行数减少（级别切换生效）
```

## 4. 可观测性评估（标准 §12）

### 4.1 observability_gap 标记

按标准 §12.2 P1 #3，QA 在 L1 验证完成后，对每个发现的 BLOCKER/MAJOR 标注 `observability_gap` 状态：

| 场景 | observability_gap | 含义 |
|------|:---:|------|
| 日志覆盖了该 finding 的根因诊断路径 | `false` | 可观测性充足 |
| 日志缺失关键信息，无法仅凭日志定位该 finding 的根因 | `true` | 可观测性缺口 |
| 该 finding 不涉及管线可观测性（如 UI 问题） | N/A | 不适用 |

**P0-05 的独特角色**：P0-05 本身就是可观测性建设任务。因此 QA 评估分为两步：
1. **实现质量评估**：P0-05 实现是否达标（本文档第 3 节测试用例）
2. **效能评估**：新日志是否实际改善了其他 Infomanager 问题的定位能力（回归验证）——这需要未来 P0-04 等依赖日志的排查任务来验证

### 4.2 可观测性回归声明

按标准 §12.1 #1（回归范围），P0-05 完成后需确认：

| 检查项 | 说明 |
|--------|------|
| 原有管线功能不受影响 | 加日志不应改变管线行为。需回归：ingest→process→store 核心路径 |
| 日志不影响性能 | INFO 模式下的日志写入不应使管线延迟增加 > 5%（绝对阈值 < 100ms） |
| 存量日志不冲突 | 如有旧的非结构化日志输出（print/logging），需确认不产生双份/冲突 |

### 4.3 长期监控建议

| 指标 | 目的 | 监控方式 |
|------|------|---------|
| ERROR 日志频率 | 管线健康度 | 每日 ERROR 计数，超过基线 3σ 告警 |
| Trace ID 完整性 | 跨阶段关联 | 无 trace_id 的日志行比例，目标 < 1% |
| 日志体积趋势 | 磁盘规划 | 每周日志体积增长趋势，超过 20%/周 告警 |
| PII 扫描 | 安全合规 | 定期（周级）正则扫描日志文件 |

## 5. 发现分级框架

### 5.1 判定公式（标准 §1.2）

P0-05 执行过程中发现的任何问题，按以下框架分级：

```
前置检查：
  └─ 是安全漏洞？（PII 泄露、日志注入等） → 是 → 最低 MAJOR（§2 + 附录 B）

正式判定（五步）：
  步骤 E — 用户可感知？→ 否 → SUGGESTION
    例外：日志缺失导致故障无法定位 → 间接用户可感知 → 仍需进入后续步骤
  步骤 F — 功能阻断？→ 否 → MINOR
  步骤 W — 有 workaround？→ 是 → MAJOR；否 → BLOCKER
  步骤 D — 数据敏感度？→ S/A/B/C（§4）
  步骤 P — 性能退化？→ §3 的绝对阈值：日志写入 > 100ms → MAJOR；> 500ms → BLOCKER
```

### 5.2 预期发现类型与预设级别

| 发现场景 | 预设级别 | 判定路径 |
|---------|:---:|---------|
| JSON schema 不满足 — 字段缺失/类型错误 | **MAJOR** | 用户可感知(日志不可解析) + 功能阻断(无法自动化) + 有 workaround(手工 grep) |
| 日志级别混乱 — INFO 输出 debug 敏感信息 | **MAJOR** | 用户可感知(日志无用) + 可能触发安全红线(PII) → 升级为 BLOCKER |
| 无 trace_id | **BLOCKER** | 用户可感知 + 功能阻断(跨阶段无关联) + 无 workaround(需改代码) |
| ERROR 无堆栈/上下文 | **MAJOR** | 用户可感知 + 功能阻断(无法定位) + 有 workaround(重新跑 DEBUG) |
| PII 泄露 | **BLOCKER** | 安全漏洞(附录 B 补充) → 最低 MAJOR，若无 workaround(已落盘) → BLOCKER |
| DEBUG 模式日志量爆炸 | **MINOR** | 用户不可感知(仅 DEBUG 模式) + 不影响核心功能 → MINOR |
| 日志写入延迟 > 100ms | **MAJOR** | 用户可感知(管线延迟) + 体验退化 + 可切换级别 workaround |
| 老旧 print 日志未清理 | **SUGGESTION** | 用户不可感知(冗余) + 无功能影响 → SUGGESTION |

### 5.3 分级示例对照表（标准 §5）

| 发现 | 最接近 §5 示例 | 类比说明 |
|------|-------------|---------|
| 无 trace_id | #1「支付按钮无响应，无替代路径」 | 核心可观测性路径完全阻断，无 workaround |
| PII 泄露 | #5「明文密码记录到日志」 | 安全漏洞，独立判定 → BLOCKER |
| JSON schema 不符 | #2「支付无响应但手动输入可绕过」 | 功能阻断 + 有 workaround（手工 grep） → MAJOR |
| ERROR 无上下文 | #17「列表页偶发白屏，刷新恢复」 | 偶发功能缺失 + 有 workaround（切 DEBUG） → MAJOR |
| 老旧 print 残留 | #15「变量命名 x → userCount」 | 用户不可感知 + 纯代码层面 → SUGGESTION |

## 6. 论证流程与 SLA

### 6.1 论证流程（标准 §6）

```
QA 发现（L1 测试用例执行结果）
  → 按 §5 预设级别标注
  → 研发评估（通过 / 驳回 / 暂缓）
    ├── 通过：记录理由 + 修复方案
    ├── 驳回：附理由（by design / cannot repro / cost > benefit）
    │   └── QA 可启动有成本申诉 → 产品裁定（§6.3-§6.4）
    └── 暂缓：记录目标版本
        └── 若为 BLOCKER → 需 Frank 签字（§11 红线 1）
```

**P0-05 特殊考虑**：实现任务尚未创建，L1 阶段可能延迟到 P1 迭代。当前测试方案一旦评审通过，QA 即可在实现任务创建后直接执行 L1，无需重新设计方案。

### 6.2 SLA 时效性（标准 §8）

| 发现级别 | 研发响应 | 定位（初步判定 + 进度同步） | 方案 | 说明 |
|:---:|:---:|:---:|:---:|------|
| BLOCKER | 4h | 8h | 24h | 影响发版决策 |
| MAJOR | 1 工作日 | 2 工作日 | 版本窗口内 | — |
| MINOR | 3 工作日 | 7 工作日 | 下版本 | — |
| SUGGESTION | — | — | — | 无时限 |

**跨时区规则**：从下一工作时段起算。

**P0-05 目前状态**：实现任务尚未创建 → 所有 SLA 计时尚未启动。SLA 从实现任务完成并进入 QA 评审之日起算。

## 7. 发布门禁（标准 §10）

P0-05 完成后，发布判定公式：

```
BLOCKER=0 AND MAJOR≤N（由产品裁定） AND 安全漏洞=0 AND 无未裁定的申诉 → 可通过
```

### 7.1 P0-05 专属门禁

| 门禁项 | 判定 |
|--------|:---:|
| L0 前置检查（C1-C6）全部通过 | ✅ 必须 |
| L1 测试用例（TC-01~TC-06）全部 PASS | ✅ 必须 |
| 无 BLOCKER 级别发现 | ✅ 必须 |
| 无 PII 泄露（安全漏洞） | ✅ 必须 |
| observability_gap 标记完成 | ✅ 必须 |
| 回归测试通过（原有管线功能不退化） | ✅ 必须 |
