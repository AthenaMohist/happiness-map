## 1. 触发事实：重复全量实测解剖

### 1.1 MEM-008 链（全量 363 跑了 4 遍）

| 环节 | 跑了什么 |
|------|---------|
| DEV（五子卡合并产物） | 全量 363（研发自测） |
| QA-EXEC t_75028424 | targeted 52 + **全量 363** |
| QA-D2 t_598a4b63 | targeted 52 + **全量 363**（同一内容再来一遍） |
| VA t_a839a252 | 独立重跑 targeted 52 + **全量 363**（第三遍） |

### 1.2 MEM-013 链（同模式）

DEV 375 → QA-EXEC 327 → QA-D2 复检 327 → VA 再 327。

### 1.3 定性

重复的不是「研发自测 + QA 终测」这种合理分工，而是**每一步都无条件跑全量**：

- 各环节本意是**互补验证**（研发自测覆盖功能、QA 覆盖验收标准、VA 覆盖证据复核），实际退化成同一动作的机械重复；
- 代码在 DEV→QA 之间未变时，第二次全量是纯冗余（确定性输入 → 确定性输出，重跑不产生新信息）；
- 成本：每遍全量数十分钟 worker 时间 × 每链 3-4 遍 × 链数量，且拉长链路时延、放大超时风险（timed_out 重试还会再跑一遍）。

## 2. 各环节测试职责分层

| 环节 | 必跑 | 禁跑 | 职责定位 |
|------|------|------|---------|
| DEV（研发自测） | **全量 pytest（节点 1）** + 改动相关 targeted | — | 自测：全量绿是 DEV done 门槛 |
| QA-EXEC | 自己测试方案的 targeted 用例 + 行为级验证 | 全量 | 验收：对照测试矩阵逐条验证 |
| QA-D2 | 报告评审 + 抽测（随机抽 2-3 个 EXEC 断言复核 + 报告逻辑检查） | 实跑全量 | 复核：验证报告质量，不是重放 EXEC |
| VA | 声明抽查 + 证据溯源（抽验 2-3 个 claim：commit 实存/文件实改/抽查一个测试真过），git/文件实锤取证 | 重跑全量 | 证据审计：威慑力在「会被抓」不在「全复跑」 |
| 合并后 main（节点 2） | **全量 pytest 一次**（合并完整性验证） | — | 终验：发布门禁语义不变（0 BLOCKER/0 MAJOR + 两节点全量绿） |

> **全部测试执行统一下沉 cc**（含 QA/VA 的跑测动作）：cc-glm 一条命令执行，Hermes 轮次只做结果判定（DPL-137 规则 5）。

------|------|------|---------|
| DEV（研发） | 改动相关的 targeted 用例 + 受影响模块测试 | — | 自测：证明实现正确 |
| QA-EXEC（QA 执行） | 验收标准映射的 targeted 用例（D1 评审确定的测试矩阵） | 全量 | 验收：对照验收标准逐条验证 |

## 3. 规则 TL1：全量回归只在两节点跑

**全量 pytest 套件在同一条链上只允许在两个节点执行，其余环节一律禁止：**

1. **节点 1 — DEV 自测**（研发 done 门槛前）：全量绿 = 研发自证实现正确；
2. **节点 2 — 合并后 main**（合并完整性验证）：发布门禁，语义不变；
3. QA-EXEC / QA-D2 / VA **禁止无条件全量**，各环节跑什么见 §2 职责矩阵。

**例外（节点外全量，必须写明触发原因）**：

- DEV 交付与 QA 执行之间代码发生了**非平凡变更**（合并冲突解决、回滚补丁、依赖升级）；
- 测试环境本身变更（Python 版本、依赖集、pytest 配置）；
- Frank 显式要求。

## 4. 规则 TL2：重复执行禁止

1. **下游环节禁止重跑上游已 PASS 的同一批用例**——上游报告（含用例清单 + 结果 + 退出码）是可引用证据，下游引用路径而非重跑；
2. QA-D2 职责 = 报告评审 + 抽测（随机抽 2-3 个 EXEC 断言复核 + 报告逻辑检查），**不是** QA-EXEC 全矩阵重放；
3. VA 职责是声明抽查 + 证据溯源（抽验 2-3 个 claim：commit 实存 / 文件实改 / 抽查一个测试真过），git/文件实锤取证，不重跑全量；
4. 卡模板验收标准措辞：QA/VA 卡**不得**出现「全量 pytest 通过」；DEV 卡的全量指节点 1 自测；合并卡的「全量回归」指节点 2（DPL-136 管线链 AC 措辞同步以此为准）。

## 5. 规则 TL3：全量失败的归因与去向

全量门禁 FAIL 时的处理路径（诚实分支，不许静默吞掉）：

```
全量 FAIL
├─ 失败项 ⊆ 该链 targeted 已覆盖范围 → 打回 DEV 修复（实现问题）
├─ 失败项 ∈ 存量债务（非本链引入）→ 记录到本链 result + 单独建 FIX 卡登记债务，本链不阻断
└─ 环境类失败（INTERNALERROR / 收集杀死）→ 按 devppl-test-spec §3/§4 排查，属测试代码违规，打回 DEV
```

## 6. 验收清单（卡模板嵌入）

各环节卡验收标准新增公共条款：

- [ ] 本卡未执行全量 pytest（或已满足 §3 例外并注明触发原因）
- [ ] 引用的上游测试结果路径真实存在且未过期（代码 commit 一致）
- [ ] 卡 result 记录：跑了哪些用例（清单/计数）、退出码、输出文件路径
- [ ] （仅合并卡）全量门禁已执行且输出文件路径已写入 result
