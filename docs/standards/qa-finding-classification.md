## 1. 四级分层与判定公式

### 1.1 级别概览

| 级别 | 一句话定义 | 发版影响 |
|------|-----------|:---:|
| **BLOCKER** | 不修不能发版 | 阻塞发版 |
| **MAJOR** | 严重影响体验，发版需标注 known issue | 尽量修复 |
| **MINOR** | 不好但用户能忍 | 不阻塞 |
| **SUGGESTION** | 做更好但不做也行 | 不阻塞 |

### 1.2 完整判定公式

```
前置检查：
  └─ 安全漏洞？ → 是 → 最低 MAJOR，进入正式判定（详见 §2）

正式判定：

  BLOCKER = (用户可感知 AND 功能阻断 AND 无 workaround)
            OR 安全漏洞（OWASP Top 10 重大级：认证绕过 / 数据泄露 / 可被远程利用的注入）
            OR 数据一致性问题（涉及 S 级数据：资金流水、用户资产、订单金额）
            OR 性能退化 P95 ≥ 10x 基准
            OR OOM/崩溃
            OR 概率性 bug（涉及资金/核心功能，即使概率极低）

  MAJOR   = (用户可感知 AND (功能阻断但有 workaround OR 体验严重退化))
            OR 安全漏洞（非 BLOCKER 级但存在安全风险，如 XSS、CSRF、SSRF）
            OR 数据一致性问题（涉及 A 级数据：用户基础信息、权限）
            OR 性能退化 P95 ≥ 3x 基准
            OR PII（个人敏感信息）泄露

  MINOR   = 用户可感知 AND 不影响核心任务完成

  SUGGESTION = 用户不可感知（非安全/非数据完整性/非系统健康度）OR 纯主观偏好
```

### 1.3 关键判定原则

| 原则 | 说明 |
|------|------|
| **「用户可感知」是第一刀** | 用户不可感知的问题（代码风格、内部重构建议）→ SUGGESTION，不参与 BLOCKER/MAJOR/MINOR 讨论。**例外**：安全漏洞、数据一致性问题不经过此过滤。 |
| **「用户可感知」的扩展定义** | = 用户可感知（UI 异常、操作失败）OR 数据完整性受影响（数据写错/丢失/不一致）OR 系统健康度退化（内存泄漏、错误率上升、MTTR 恶化）。 |
| **「workaround 是否存在」是第二刀** | 用户能被临时方案解救的，从 BLOCKER 降为 MAJOR。 |
| **概率性 bug：以最坏情况定级** | 偶发崩溃、竞态条件、并发数据错乱——以「最坏情况下用户影响」为准，附带复现率数据。 |
| **无法判断级别时：默认取高级别** | QA 无法判断属于哪个级别时（两个级别都说得通），取高级别 + 标注 `triage_needed`，由研发评估时确认或降级。 |
| **环境差异不降级** | Bug 级别按 production 影响定级，不因只在特定环境复现而降低级别。标注 `env:specific` 作为风险信号。 |

## 2. 安全漏洞独立判定

安全漏洞**不经过「用户可感知」过滤**——安全问题的本质是「潜在的」用户影响，当它变成「可见的」时，已经发生了安全事故。

### 2.1 判定规则

| 安全漏洞类别 | 判定 | 最低级别 |
|-------------|:---:|:---:|
| 认证绕过、数据泄露、可被远程利用的注入（SQL 注入等） | 独立判定 | **BLOCKER** |
| XSS、CSRF、SSRF、敏感信息泄露（非 PII）、内部横向移动风险 | 独立判定 | **MAJOR** |
| PII（个人敏感信息）泄露（手机号、身份证、实名信息等） | 独立判定 | **MAJOR+** |
| CVSS ≥ 4.0 的漏洞 | 独立判定 | 按 CVSS 严重度对应 |

### 2.2 边界限定

- 安全漏洞判定范围限定在 OWASP Top 10 大类（见附录 B），不能泛化。
- QA 对照 Checklist 做分类，不要求执行渗透测试。
- 研发不能以「未来可能导致安全问题」为由将非安全类 SUGGESTION 升级——必须属于 OWASP Top 10 范畴。

## 3. 性能退化量化阈值

### 3.1 正式阈值（APM baselining 就绪后）

| 退化幅度（P95 vs 基准） | 级别 |
|------------------------|:---:|
| 响应时间恶化 ≥ 10x 基准，或触发 OOM/崩溃 | **BLOCKER** |
| 响应时间恶化 ≥ 3x 基准 | **MAJOR** |
| 响应时间恶化 < 3x 基准 | MINOR |

### 3.2 Fallback 绝对阈值（APM 未就绪时过渡）

| 响应时间 | 级别 | 说明 |
|----------|:---:|------|
| < 1s | MINOR | 用户可能注意到 |
| 1s – 5s | MAJOR | 体验严重退化 |
| > 5s 或 OOM/崩溃 | BLOCKER | 功能实质上不可用 |

> APM 就绪后切换为相对阈值（3x/10x）。Issue 系统同时记录绝对时间和相对退化两个值，便于 APM 上线后回溯校准。

## 4. 数据敏感度加权

涉及特定敏感度数据的一致性问题，在原判定基础上自动加权。

| 敏感度 | 包含数据 | 遇到一致性 bug 时 |
|--------|---------|:---:|
| **S 级** | 资金流水、用户资产、订单金额 | 自动 → **BLOCKER** |
| **A 级** | 用户基础信息（手机/邮箱/实名）、权限数据 | 自动 +1 级 → 最低 **MAJOR** |
| **B 级** | 用户行为日志、统计指标 | 不加权 |
| **C 级** | 内部配置、管理后台数据 | 按正常公式 |

完整数据敏感度分类表见附录 A。

## 6. 论证流程

### 6.1 基础流程

```
QA 发现 → 按判定公式标注级别 → 研发评估 → 三种结果：
  ├── 通过（agree）    → 按级别默认策略处理
  ├── 驳回（reject）    → QA 可接受或申诉
  └── 暂缓（defer）     → 记录目标版本，降低优先级
```

### 6.2 各结果判定标准

**通过（agree）**：
- 研发认可 QA 级别 → 直接通过
- 研发修正级别（如 BLOCKER→MAJOR）→ 修正后通过，需附理由
- 级别偏高但影响不大 → 按原级别通过（不纠结）

**驳回（reject）——必须附驳回理由**：
- 非 bug（by design / 预期行为）→ 标注 `won't fix / by design`
- 无法复现 → 标注 `cannot repro`，需附研发尝试复现的环境信息 + 尝试次数（BLOCKER ≥ 20 次，MAJOR ≥ 10 次）
- SUGGESTION 级别，改的成本 > 收益 → 标注 `cost > benefit`

**暂缓（defer）**：
- MINOR/SUGGESTION，当前版本排期已满 → 标记目标版本
- MAJOR，有 workaround 且修复成本高 → 先发版标注 known issue，下版本修
- BLOCKER，影响非主路径（冷门功能、内测用户专属）→ **需 Frank 确认**后才能暂缓

### 6.3 申诉机制（有成本申诉）

```
研发驳回 issue（必须附驳回理由）
  └── QA 两个选择：
        ├── 接受 → issue 关闭，标注 accepted rejection
        └── 申诉 → status: appeal
              ├── 必须附带：新复现证据 / 新影响面分析 / 新用户反馈
              ├── 产品（许清楚）直接裁定，跳过二轮研发
              ├── 产品裁定结果：维持驳回 / 恢复并调整级别
              └── 产品裁定为最终裁定，不可二次申诉
```

**申诉规则**：
- QA 不能空手申诉——「我觉得这很重要所以必须修」不是有效申诉理由。
- 产品从用户影响角度裁定，不陷入技术细节争议。
- 追踪申诉率：申诉率 > 20% → 说明判定公式有歧义，需 refine。

### 6.4 研发降级透明度

当研发改变 QA 原始级别时（BLOCKER→MAJOR, MAJOR→MINOR）：
- **自动通知产品知晓**（信息对称，非审批）
- 降级必须附理由（如「有 workaround：用户可以手动输入金额绕过」）
- 产品作为 observer 而非 gatekeeper——不阻塞研发动作，仅感知降级行为
- 建议以 daily digest 形式汇总

## 7. Bug 生命周期状态机

```
[NEW] ──QA提交──→ [OPEN] ──研发评估──→ [CONFIRMED] ──研发修复──→ [RESOLVED] ──QA回归──→ [CLOSED]
  │                  │                     │                           │                │
  │                  ├──驳回──→ [REJECTED] ──QA申诉──→ [APPEAL] ──产品裁定──→ 维持驳回 → [CLOSED]
  │                  │                     │                           │           │
  │                  │                     └──QA接受──→ [CLOSED]       │           └──恢复 → [CONFIRMED]
  │                  │                     │                           │
  │                  └──暂缓──→ [DEFERRED] ──版本到达──→ [OPEN]        └──修复无效──→ [REOPENED] ──研发重新确认──→ [CONFIRMED]
  │                  │                                                          │
  │                  └──重复──→ [DUPLICATE] ──链接到主 bug                       │
  │                                                                             │
  └──QA自行撤回──→ [WITHDRAWN]
```

### 7.1 状态权限矩阵

| 状态转换 | QA | 研发 | 产品 | 备注 |
|---------|:---:|:---:|:---:|------|
| NEW → OPEN | ✅ | — | — | QA 提交 |
| OPEN → CONFIRMED | — | ✅ | — | 研发确认 |
| OPEN → REJECTED | — | ✅ | — | 需附驳回理由 |
| OPEN → DEFERRED | — | ✅ | ✅ | 暂缓需标注目标版本 |
| OPEN → DUPLICATE | — | ✅ | — | 需链接主 bug |
| REJECTED → APPEAL | ✅ | — | — | 需附新证据 |
| APPEAL → CONFIRMED | — | — | ✅ | 产品裁定 |
| APPEAL → CLOSED | — | — | ✅ | 产品裁定 |
| CONFIRMED → RESOLVED | — | ✅ | — | 修复完成 |
| RESOLVED → CLOSED | ✅ | — | — | QA 回归通过 |
| RESOLVED → REOPENED | ✅ | — | — | QA 回归不通过 |
| REOPENED → CONFIRMED | — | ✅ | — | 研发重新确认并修复 |
| DEFERRED → OPEN | — | ✅ | — | 版本到达，重新激活 |
| OPEN → WITHDRAWN | ✅ | — | — | QA 自行撤回 |

## 8. SLA 时效性

### 8.1 研发侧 SLA（三档拆分）

| 级别 | 响应时限 | 定位时限 | 方案时限 |
|------|:---:|:---:|:---:|
| **BLOCKER** | 4h | 8h（初步判定 + 进度同步） | 24h |
| **MAJOR** | 1 工作日 | 2 工作日 | 当前版本窗口内 |
| **MINOR** | 2 工作日 | — | 不限 |
| **SUGGESTION** | 3 工作日 | — | 不限 |

**关键定义**：

- **响应时限**：研发确认收到 issue 并给出初步判断（确认/驳回/暂缓）。不是「回一条消息」，而是「开始处理」。
- **定位时限（BLOCKER）**：8h 内产出**初步判定 + 进度同步**——
  - 问题涉及哪些系统/模块？
  - 已排除哪些假设？
  - 当前排查方向是什么？
  - 是否需要跨团队协调？需要找谁？
  - 预计还需要多少时间完成根因定位？
- **方案时限（BLOCKER）**：24h 内产出一个决策点——**修复方案** OR **workaround 方案** OR **确认暂缓（需 Frank 签字）**。不是要求 24h 修好代码。
- **跨时区规则**：从下一个工作时段起算。不要求 24/7 值守。

### 8.2 特殊场景 SLA 调整

| 场景 | SLA 调整 |
|------|---------|
| **跨团队 handoff** | handoff 确认时间计入研发响应时限。被调团队响应时限独立起算（BLOCKER 级别被调方也是 4h）。无法按时响应 → 研发升 flag 通知产品协调。 |
| **第三方依赖阻塞** | BLOCKER 的方案时限放宽至 48h（第三方响应时间不可控），但 4h 响应时必须明确判定为「第三方依赖阻塞」。 |
| **环境差异无法复现** | SLA 计时应暂停等待环境/数据就绪（研发申请 staging 调试权限 or 脱敏数据）。环境差异**不**作为驳回理由——只能作为 SLA 暂停理由。 |
| **QA 未提供充分复现信息** | SLA 计时暂停。QA 需在 BLOCKER 2h / MAJOR 1 工作日内补充。超时未补充 → 级别可降一级。**例外**：概率性 bug 已有最佳可用证据（录屏/日志/trace ID）但研发仍难复现 → 不降级，标记 `hard_to_repro`。 |

### 8.x EXEC/D2 职责分层（DPL-137，2026-09-05 Frank 裁定）

测试执行采用分层收敛（权威源：`docs/standards/test-execution-layering-spec.md` v1.1 §2 职责矩阵、§3 TL1-TL3），本节为 QA 分级语境下的职责措辞：

| 环节 | 职责 | 全量回归 |
|------|------|:---:|
| DEV 自测 | 全量 pytest（DEV done 门槛前，节点 1） | ✅ 唯一前置全量 |
| QA-EXEC | 只跑自己测试方案用例（targeted + 行为级验证） | ❌ 禁止 |
| QA-D2 | 报告评审 + 抽测（随机抽 2-3 个 EXEC 断言复核 + 报告逻辑检查） | ❌ 禁止 |
| 合并后 main | 合并完整性验证（节点 2 全量） | ✅ 唯一合并后全量 |

发布门禁语义不变：0 BLOCKER/0 MAJOR + 两节点全量绿。

## 9. QA 侧 SLA

| 阶段 | QA 职责 | 时限 | 依赖 |
|------|---------|:---:|------|
| 发现 → 提交 | 复现、截图/录屏、日志收集、环境标注 | 发现后 1h 内提交 | QA 需有复现环境 |
| 提交 → 研发响应 | 等待研发 acknowledge | — | 研发 SLA |
| 研发响应 → QA 确认 | 验证研发的判定（agree/disagree/escalate） | 收到响应后 2h 内 | — |
| 修复完成 → QA 回归 | 定向回归测试，验证修复 + blast radius | BLOCKER 4h 内 / MAJOR 1 工作日 | 需有回归环境 + 回归用例 |
| 回归通过 → 关闭 | 确认修复有效，关闭 issue | 回归通过后即时 | — |

### 9.1 QA 提交复现证据要求

| 要求 | BLOCKER | MAJOR | MINOR | SUGGESTION |
|------|:---:|:---:|:---:|:---:|
| 复现步骤（numbered steps） | **必须** | **必须** | 建议 | 不需要 |
| 环境信息（OS/浏览器/版本/设备） | **必须** | **必须** | 建议 | 不需要 |
| 截图/录屏 | **必须** | 建议 | 建议 | 不需要 |
| 日志/Trace ID | **必须** | 建议 | 不需要 | 不需要 |
| 复现率（N/M 次） | **必须** | **必须** | 建议 | 不需要 |
| 预期行为 vs 实际行为 | **必须** | **必须** | **必须** | 建议 |

### 9.2 SLA 前置基础设施条件

以下 4 项缺失任何一项，SLA 均为空谈：

| # | 前置条件 | 缺失后果 |
|---|---------|---------|
| 1 | **标准化 bug report 模板** | 研发收到「it doesn't work」→ 4h 响应全花在追问信息上 |
| 2 | **QA 可用的复现环境** | 「cannot repro」驳回率 > 50% |
| 3 | **日志/Trace 可获取性** | 研发的定位时限从第 0 分钟就已破裂 |
| 4 | **BLOCKER 中断当前工作的制度保障** | 「4h 响应」可以做到（抽 5 分钟看 issue），但「8h 定位 + 24h 方案」需要实际投入 coding/debugging 时间 |

---

## 10. 发布门禁

| 级别 | 代码审查 | 测试门禁 | 发布策略 |
|------|:---:|------|------|
| **BLOCKER** | ✅ 必须第二人 review | staging smoke test（QA 执行） | 灰度发布（如有能力），灰度 30min 无明显退化后全量 |
| **MAJOR** | ✅ 推荐 review | staging 回归测试（QA 执行，覆盖核心路径） | 常规发布 |
| **MINOR** | 不强制 | 常规 CI | 常规发布 |
| **SUGGESTION** | 不强制 | 常规 CI | 常规发布 |

### 10.1 回归测试范围

| 修复级别 | 回归范围 | 时间预算 |
|---------|---------|:---:|
| BLOCKER | 修复模块 + 1 级依赖模块 + 核心用户路径冒烟测试 | 4h |
| MAJOR | 修复模块 + 1 级依赖模块 | 2h |
| MINOR | 修复模块的单元测试 + 1 个关键场景 | 1h |
| SUGGESTION | 无需回归（或研发自行判断） | — |

> **「1 级依赖模块」定义**：直接调用或被修复模块调用的模块（通过 import / API call / 数据库表关联判断）。QA 在回归前与研发确认依赖模块清单。

### 10.2 跨团队修复的回归时限

跨团队 BLOCKER 修复的 QA 回归时限从「所有相关团队修复部署到 staging 后」起算，而非从「修复代码提交后」起算。

## 11. 产品红线

| 红线 | 内容 | 理由 |
|------|------|------|
| **红线 1** | BLOCKER 暂缓必须 Frank 签字 | BLOCKER 的定义是「不修不能发版」，暂缓等于推翻这个定义，需要 project owner 级别授权。 |
| **红线 2** | 申报诉必须带新证据 | 空手争论不构成有效申诉——「有成本」的「成本」在于证据门槛。 |
| **红线 3** | 产品裁定为最终裁定，不可二次申诉 | 防止申诉机制变成新的消耗战。 |

## 附录A：数据敏感度分类表

| 敏感度 | 包含数据 | 遇到一致性 bug 时的级别影响 | 示例 |
|--------|---------|:---:|------|
| **S 级** | 资金流水、用户资产（积分/余额/虚拟币）、订单金额、支付记录 | 自动 → **BLOCKER** | 订单金额并发计算错误 |
| **A 级** | 用户基础信息（手机号/邮箱/实名认证信息）、权限/角色数据、账户状态（封禁/注销） | 自动 +1 级，最低 **MAJOR** | 权限数据缓存不一致导致越权 |
| **B 级** | 用户行为日志、统计指标（DAU/留存率/转化率）、偏好设置（非关键） | 不加权 | 统计数据展示延迟 |
| **C 级** | 内部配置项、管理后台数据、非用户侧的运营数据 | 按正常公式 | 内部管理后台的排序错误 |

> 使用方式：QA 提交 bug 时选择 `data_sensitivity` 字段（S/A/B/C），系统自动计算加权。研发在评估时可修正。

## 附录B：安全漏洞 Checklist（OWASP Top 10）

QA 提交 bug 时对照此 Checklist 判断是否属于安全漏洞范畴。不要求执行渗透测试——只需能识别类别。

| # | OWASP 类别 | 典型表现 | 一旦确认的最低级别 |
|---|-----------|---------|:---:|
| A1 | 访问控制失效（Broken Access Control） | 越权访问他人数据、普通用户执行管理员操作、认证绕过 | **BLOCKER** |
| A2 | 加密失效（Cryptographic Failures） | 明文传输密码/Token、弱加密算法、硬编码密钥 | **BLOCKER** |
| A3 | 注入（Injection） | SQL 注入、命令注入、LDAP 注入 | **BLOCKER**（可远程利用） |
| A4 | 不安全设计（Insecure Design） | 缺少速率限制导致可暴力破解、业务流程可被绕过 | **MAJOR** |
| A5 | 安全配置错误（Security Misconfiguration） | 默认账号密码未修改、错误信息暴露堆栈、不必要的端口开放 | **MAJOR** |
| A6 | 易受攻击和过时的组件（Vulnerable Components） | 使用了已知 CVE 的第三方库版本 | **MAJOR**（CVSS≥7 → BLOCKER） |
| A7 | 身份认证失效（Identification and Authentication Failures） | 弱密码策略、会话固定攻击、凭证填充可被利用 | **MAJOR** |
| A8 | 软件和数据完整性失效（Software and Data Integrity Failures） | 反序列化漏洞、未验证的更新包、CI/CD 管道污染 | **BLOCKER**（可远程利用） |
| A9 | 安全日志和监控失效（Security Logging and Monitoring Failures） | 无审计日志、日志可被篡改、安全事件无告警 | **MAJOR** |
| A10 | 服务端请求伪造（SSRF） | 可被利用访问内部系统 | **MAJOR** |

**补充**：
- **PII 泄露**（个人敏感信息：手机号、身份证号、实名信息、银行卡号、家庭住址）→ 按安全漏洞处理，最低 **MAJOR**。
- **内部横向移动风险**（一个被攻破的微服务可访问其他微服务的未授权接口）→ 最低 **MAJOR**。

## 附录C：性能退化 Fallback 绝对阈值（APM 就绪前过渡方案）

| 响应时间 | 级别 | 说明 |
|----------|:---:|------|
| < 1s | MINOR | 用户可能注意到 |
| 1s – 5s | MAJOR | 体验严重退化 |
| > 5s 或 OOM/崩溃 | BLOCKER | 功能实质上不可用 |

> APM baselining 就绪后切换为相对阈值（3x/10x）。Issue 系统建议同时记录绝对时间（当前可测）和相对退化（APM 就绪后可追算），便于回溯校准。
